## Развитие (с 2026-09-26): от клиента к ядру уровня Xray/sing-box

Полный план по фазам (0–8) — в документе «План развития» (Claude Docs);
здесь — решения и итог по сделанным фазам.

### Фаза 0 — архитектура «входы → маршрутизатор → выходы» ✅

- `core/src/app/`: трейты `Outbound` (TCP `connect`, UDP `udp` →
  `UdpSession`) и вход, который по `Metadata` (вход, источник, сеть,
  назначение, порт, найденный домен) спрашивает `Router`. Выходы `vless`
  (с XUDP или потоком на назначение), `direct`, `block`.
- Файл настроек TOML (`--config`, `--check`), `deny_unknown_fields` —
  опечатка в поле даёт ошибку, а не «молча не задано». Ключи CLI собирают
  тот же `Config`: одна проверка настроек на оба способа.
- UDP-ассоциация держит по одной сессии на выбранный выход; ответы всех
  сессий идут владельцу ассоциации.
- Безопасность: `direct` не соединяет клиентов из сети с адресами этого
  компьютера (`127.0.0.1`, `localhost`, проверка по фактическому адресу
  после разрешения имени) — иначе прокси, открытый в сеть, отдавал бы
  соседям службы, слушающие только loopback.

### Фаза 1 — HTTP/mixed, правила, sniffing, системный прокси ✅

- Входы `socks`, `http`, `mixed` (вид — по первому байту). HTTP: CONNECT
  и обычные запросы (строка запроса → origin-form, заголовки прокси
  убираются, `Connection: close` — чтобы следующий запрос по тому же
  соединению не ушёл не на тот сайт; WebSocket `Connection: Upgrade`
  сохраняется). Пароль — `Proxy-Authorization: Basic`, тот же счётчик
  неверных паролей, что у SOCKS5; запрос без пароля ошибкой не считается
  (браузер сначала спрашивает без него).
- Правила как у sing-box: `(домен ИЛИ адрес) И порт И сеть И вход`, первое
  подошедшее. Домены: точное совпадение и суффикс — через `HashSet` и
  перебор родительских доменов, подстроки, `RegexSet`. Адреса — слитые
  отсортированные диапазоны с двоичным поиском. На настоящих базах v2fly
  (`category-ads-all` + `category-ru` + `geoip:ru,private`) — 0,2 с на
  загрузку в debug, ~0,4 мкс на проверку.
- `geosite.dat`/`geoip.dat` — свой разбор protobuf (varint и поля с
  длиной), из файла берутся только нужные категории; повреждённый файл —
  ошибка, не паника (тест на мусоре). Выражения из geosite, которые не
  разбирает `regex` (RE2-диалект), пропускаются поштучно.
- Sniffing TLS SNI / HTTP Host — только когда приложение прислало IP:
  ответ «соединено» уходит раньше, чем открыт выход (иначе приложение не
  пришлёт байт), поэтому ошибку потом можно сообщить только закрытием.
  Ждём не дольше 300 мс (протоколы, где первым говорит сервер).
  `sniff_override_destination` отдаёт выходу домен вместо IP.
- `--system-proxy` (Windows): `ProxyEnable/ProxyServer/ProxyOverride` в
  HKCU + `InternetSetOption`; прежние значения (включая отсутствие
  значения) возвращаются при Ctrl+C/закрытии окна/выходе из системы;
  `--system-proxy-off` — после жёсткого завершения. Проверено под Wine:
  unit-тест реестра и сквозной запуск с SIGINT.
- Не сделано в фазе 1: QUIC-sniffing (Initial с ClientHello Chrome на
  двух пакетах), наборы правил sing-box `.srs`, разрешение имён для
  IP-правил (`IPIfNonMatch`) — это Фаза 2 (DNS).

### Фаза 2 — DNS ✅

- `core/src/app/dns/`: серверы UDP/TCP/DoT/DoH/`local`/`fakeip`
  (`upstream.rs`), выбор по доменным правилам и geosite (тот же
  `DomainSet`, что у маршрутизатора), кеш по TTL с пределом размера
  (`cache.rs`), fake-IP с кольцевой выдачей и сохранением в файл
  (`fakeip.rs`). Разбор и сборка сообщений — `hickory-proto` (только
  формат, свой транспорт).
- Серверы ходят через выходы (`detour`, по умолчанию `route.final`): DoH
  через VLESS — провайдер не видит имён. UDP к DNS через VLESS — XUDP
  (проверено против Xray в smoke). Ответ принимается, только если совпали
  номер, флаг ответа, вопрос и адрес сервера. Большой ответ по UDP
  (TC) — повтор по TCP; клиенту без EDNS по UDP — урезанный с TC.
- Петли: выход `direct` для запросов самого DNS-модуля разрешает имя
  сервера системно (метка `dns-internal`); `detour` на выход `dns` —
  ошибка настроек. Имя VLESS-сервера — системным резолвером с кешем
  (120 с, при сбое DNS — прежние адреса до часа): закрыт открытый пункт
  аудита про кеш DNS сервера.
- Вход `dns` (UDP+TCP, 256 запросов одновременно), выход `dns` (перехват
  по правилу `port = [53]`), `direct` через модуль,
  `route.domain_strategy = "ip_if_non_match"` (требует `[dns]` — иначе
  имена уходили бы системному DNS мимо туннеля). Fake-IP в маршрутизаторе
  заменяется именем; неизвестный fake-IP — отказ; UDP к fake-IP — своя
  сессия на адрес, ответы подписываются fake-IP.
- DNS-вход в сеть без `allow_ip` не запускается (открытый резолвер).
- `Error::Protocol` больше не пишет «VLESS protocol error» перед каждым
  сообщением: ошибки DNS, direct и HTTP к VLESS не относятся.
- Проверено: 7 интеграционных тестов (`core/tests/app_dns.rs`: UDP/TCP,
  кеш, TC, DoT, DoH, недоверенный сертификат, fake-IP TCP и UDP, перехват,
  `ip_if_non_match`, ошибки настроек), smoke через Xray. Настоящие
  публичные DoH/DoT из песочницы недоступны (её шлюз подменяет
  сертификаты — клиент правильно отказывается), поэтому проверить их
  можно только на своей машине.
- Не сделано: DNS over QUIC и HTTP/3, ECS, отдельный кеш по серверу для
  одинакового имени — не нужно; перехват DNS в TUN — Фаза 3.

### Фаза 3 — TUN ✅ (Linux), 🟡 Windows (собирается, не проверен)

- Устройство — `tun-rs` (Linux: /dev/net/tun; Windows: Wintun,
  `wintun.dll` рядом с программой), свой TCP/IP-стек — `ipstack` (TCP- и
  UDP-потоки из пакетов). Соединения из TUN идут тем же путём, что из
  SOCKS5: sniffing → маршрутизатор (fake-IP → имя) → выход.
- Петля «клиент → TUN → клиент» закрыта `net_protect`: все исходящие
  сокеты (VLESS, `direct`, DNS) на Linux получают `SO_MARK 0x7e2`, на
  Windows привязываются к физическому интерфейсу (`IP_UNICAST_IF`).
- `auto_route` на Linux — как у sing-box: таблица 2022 с маршрутом по
  умолчанию через TUN, правила `fwmark → main`, `route_exclude → main`,
  `всё → 2022`, при `strict_route` — `unreachable` (kill switch).
  Убитый клиент: интерфейс исчезает с маршрутами, таблица пустеет — сеть
  работает (или закрыта при `strict_route` до `--tun-cleanup`). На
  Windows — маршруты `0.0.0.0/1`, `128.0.0.0/1` (и IPv6) через `netsh`,
  DNS интерфейса = соседний адрес TUN (перехватывается), метрика 1.
- Имена VLESS- и DNS-серверов разрешаются до включения маршрутов и
  дальше берутся из кеша (обновление в фоне): с TUN системный DNS сам
  идёт через клиент, ждать его в пути соединения — петля. Сервер
  `local` вместе с TUN — ошибка настроек.
- IPv6: адрес `fdfe:dcba:9876::1/126` по умолчанию, чтобы IPv6 не шёл
  мимо TUN; в системе без IPv6 тихо выключается (явно заданный — ошибка).
- Настройки `ipstack`: окно 512 КиБ, простой 1 ч (по умолчанию 16 КиБ и
  60 с). Опция MSS в SYN-ACK с `ipstack` 1.0 теряла соединения (4 из 4
  прогонов) — не ставится; без неё 5 из 5, ~85 МиБ/с через TUN+VLESS.
- Проверено: `scripts/tun_netns.sh` — отдельное сетевое пространство с
  veth к хосту, где Xray, эхо и DNS: TCP, 32 МиБ, `direct` без петли,
  `route_exclude`, UDP/XUDP, перехват DNS к 8.8.8.8 (настоящий ответ и
  fake-IP), соединение с fake-IP, Ctrl+C, `kill -9`, остатки прошлого
  запуска, kill switch и `--tun-cleanup`. Добавлен в `scripts/ci.sh`.
- Не сделано: kill switch и IPv6-исключения на Windows, ICMP, QUIC-
  sniffing; Windows целиком ждёт проверки на настоящей машине.

### Главное: настоящий Xray-core как стенд

Релизы Xray с GitHub и `proxy.golang.org` в этой среде закрыты, но `git`
по GitHub работает. Собраны Go 1.27.1 из исходников и Xray-core 26.9.9
со всеми ~55 зависимостями по git (`scripts/build_xray_from_source.sh`).
На этом стенде — `core/tests/interop_xray.rs` (11 тестов) и
`scripts/smoke_xray.sh`. Впервые проверяется не «своя реализация против
своей», а клиент против того самого сервера, с которым его будут
использовать. Стенд сразу нашёл четыре серьёзные ошибки, которых не
видели все прежние тесты (ниже).

### Ошибки, найденные по ходу (все исправлены, у каждой есть тест)

1. **`security=none` на деле включал TLS.** `connect_tls_by_security`
   сводил `None` и `Tls` в одну ветку. Ссылки на серверы без TLS не
   работали вообще. Теперь это голый TCP (`SecureStream::Plain`).
2. **gRPC зависал с любым настоящим Xray.** Клиент ждал заголовков ответа
   HTTP/2 до отправки заголовка VLESS, а grpc-go шлёт их только вместе с
   первым сообщением. Свой тестовый h2-сервер отвечал сразу, поэтому
   раньше не ловилось.
3. **REALITY не работал с сайтами-приманками без ML-KEM.** В key_share
   была только гибридная доля; обычный OpenSSL < 3.5 выбрать её не может,
   и сервер отвечал «target sent incorrect server hello». Теперь, как у
   Chrome, X25519-часть гибрида идёт ещё и отдельной долей.
4. **gRPC буферизовал без ограничения** при медленном сервере
   (`send_data` без учёта окна HTTP/2). Теперь `reserve_capacity`/`poll_capacity`.
5. Мелочи: неизвестные `type=`/`security=` молча превращались в tcp/none
   (теперь ошибка); релей мог не дописать хвост, если сокет был занят, а
   приложение замолчало (добавлен flush); `cargo fmt --check` падал —
   CI ломался на первом шаге; устаревшие комментарии в `lib.rs`, `grpc.rs`,
   `fingerprint/`.

### XTLS Vision

`core/src/vless/vision.rs` — перенос `proxy/proxy.go` Xray-core с
сохранением порядка решений: padding (UUID в первом блоке, длинный
padding до 900+ байт для коротких пакетов), фильтр первых 8 пакетов
(ClientHello/ServerHello, TLS 1.3 и шифр), команды Continue/End/Direct,
переход на прямую передачу раздельно для каждого направления, заголовок
VLESS вместе с первыми данными или через 500 мс тишины.

Две находки, без которых Vision работал «иногда»:
- **rustls читает вперёд.** После блока `Direct` сервер пишет в TCP сырые
  рекорды внутреннего TLS. Go читает внешний TLS по рекорду, а rustls
  забирает из сокета сколько дадут и расшифровывает всё. Решение —
  `transport/raw.rs`: в режиме Vision сокет отдаёт rustls ровно один
  рекорд за раз, остаток держит у себя (аналог `rawInput` у Go).
- **tokio-rustls тоже читает вперёд.** Его `poll_read` дочитывает
  следующие рекорды, пока в буфере есть место, — проглатывал сырые байты
  после `Direct` и ещё отправлял alert в поток. Поймано интероп-тестом как
  плавающий DecryptError (1 из 3–5 прогонов). Vision читает через
  `poll_fill_buf` (ровно один рекорд), после исправления 20 из 20.

И третья, найденная smoke-тестом: буфер релея был ровно 16 КиБ, а полный
TLS-рекорд — 16 КиБ + заголовок. При крупных отправках Vision никогда не
видел целого рекорда и не переключал отправку на прямую передачу. Буфер
стал 17 КиБ.

Ограничения — как у Xray: только `type=tcp` с `tls`/`reality`; UDP идёт
без Vision (сервер Xray это разрешает и Vision-аккаунту); Mux/XUDP нет.

### ClientHello как у Chrome 133

Патч rustls: `ClientConfig::chrome_hello` (`ChromeHello`) и сырые
расширения в `ClientExtensions` (перемешиваются вместе с остальными).
`fingerprint::apply_chrome_extensions`:
`renegotiation_info` вместо SCSV, `signature_algorithms` — 8 схем Chrome
(Ed25519 для подписи REALITY-сервера принимается верификатором, как у
utls), SCT, `compress_certificate` brotli с настоящей распаковкой
(`brotli-decompressor`; фича `brotli` у rustls добавляла компрессор и
+1,3 МБ, свой распаковщик — +0,4 МБ), ECH GREASE, для REALITY ещё
`session_ticket`, TLS 1.2 в `supported_versions`, 6 legacy suite'ов и ALPS.

Итог (тест `core/tests/fingerprint_chrome_full.rs`): REALITY — JA4
`t13d1516h2_8daaf6152771_d8a2da3f94cd`, как у Chrome 131+; обычный TLS —
`t13d0915h2_…`. В обычном TLS два отличия оставлены осознанно: legacy
suite'ы (решение пользователя) и ALPS — если сервер на BoringSSL (CDN) его
согласует, клиент обязан ответить своими настройками в зашифрованных
расширениях, а rustls этого не умеет. В REALITY это не грозит:
Go-сервер ALPS не согласует, а сайт-приманка рукопожатие с нами не
завершает. `scripts/check_chrome_fingerprint.sh` теперь сверяет с utls
ещё и набор расширений и `signature_algorithms`.

### ML-DSA-65, UDP, SOCKS5

- `pqv=`: подпись ML-DSA-65 над HMAC-SHA512(AuthKey; ключ сертификата ||
  ClientHello || ServerHello), как в `reality.go`. Проверка — через
  aws-lc (уже в проекте, новой криптобиблиотеки нет). Патч rustls отдаёт
  хуку сырой ServerHello. Проверено против Xray с `mldsa65Seed`, включая
  отказ при чужом ключе.
- UDP: SOCKS5 UDP ASSOCIATE (`socks5/udp.rs`) → VLESS-команда UDP, по
  потоку на назначение, пакеты с 2-байтной длиной; закрытие по 120 с
  тишины; датаграммы только с IP владельца ассоциации.
- Логин/пароль (RFC 1929, сравнение без раннего выхода); без `--auth`
  клиент отказывается слушать не на loopback.
- `--ca` для самоподписанных серверов, `alpn=` и `host=` из ссылки.

## Доработка, часть 2 (2026-09-26): транспорты, XUDP, Windows

Запрос: «продолжай работать» — закрыть оставшееся из списка выше.

### httpupgrade

`core/src/transport/httpupgrade.rs`: запрос Upgrade как у Xray (порядок
заголовков как у Go, `Connection: Upgrade`, `Upgrade: websocket`), строгая
проверка ответа 101, данные после ответа — сырые. Заодно общий модуль
`browser_headers.rs` — перенос `common/utils/browser.go` из Xray: заголовки
Chrome (User-Agent с версией, вычисляемой от даты, Sec-CH-UA, Sec-Fetch-*)
теперь и у ws. Путь `?ed=2048` (ранние данные Xray) отбрасывается.
`VlessConfig::validate()` отвергает REALITY с ws/httpupgrade — Xray такое
не принимает («REALITY only supports RAW, XHTTP and gRPC»).

### xhttp (SplitHTTP)

`core/src/transport/xhttp.rs`, по исходникам `transport/internet/splithttp`:

- режимы `packet-up` (GET вниз + POST'ы с `seq`), `stream-up` (GET вниз +
  потоковый POST), `stream-one` (один POST в обе стороны); `auto` — как у
  Xray: REALITY → stream-one, иначе packet-up;
- версия HTTP — как у Xray: REALITY → h2, без TLS → HTTP/1.1, TLS → h2,
  с `alpn=http/1.1` → HTTP/1.1 (только packet-up; свой разбор chunked,
  POST'ы подряд по keep-alive без ожидания ответов, ответы проверяет
  отдельная задача, закрытое сервером соединение заменяется новым);
- маскировка — `Referer` с `x_padding` (сервер проверяет длину), заголовки
  Chrome «fetch», `Content-Type: application/grpc` у потоковых POST;
- `extra=` (JSON) — поддерживаемые ключи разбираются, меняющие формат
  запросов — понятная ошибка при старте (`validate()`), серверные и
  безвредные — пропускаются;
- ошибки сервера (404 — путь/host, 400 — padding/режим) доходят до
  приложения текстом, а не «соединение закрыто»;
- h2 с настройками SETTINGS/окнами как у Chrome (6 МиБ поток, 15 МиБ
  соединение) — заодно без узкого места в 64 КиБ по умолчанию.

Интероп против Xray-core: HTTP/1.1 без TLS (1 МиБ, мелкие POST'ы с
`scMaxEachPostBytes`, пауза 6 с посреди сессии), h2 поверх TLS во всех
трёх режимах, HTTP/1.1 поверх TLS, все режимы поверх REALITY; отказы 404
(путь, host) и 400 (padding вне диапазона — это заодно доказывает, что
сервер действительно проверяет наш `Referer`). Первый прогон нашёл
гонку в самом тесте (отказ мог прийти уже в `dial`), 15 прогонов подряд
после исправления — без сбоев.

Не сделано: `xmux` (переиспользование соединений между сессиями), HTTP/3,
`downloadSettings`, `xPaddingObfsMode`, размещение session/seq/данных не в
пути/теле.

### XUDP

`core/src/vless/xudp.rs` + `socks5::udp::serve_associate_xudp`. Выяснено по
исходникам: клиент Xray отправляет UDP через XUDP (команда Mux,
`v1.mux.cool:666`, кадры Mux.Cool одной сессии с адресом у каждого
пакета) всегда при Vision и по умолчанию без него. Сервер при flow Vision
команду UDP вообще отвергает — раньше клиент обходил это, отправляя UDP
без flow. Теперь UDP по умолчанию идёт через XUDP (с Vision — тоже, как у
Xray): одно соединение на всю SOCKS5-ассоциацию вместо одного на каждое
назначение и Full Cone NAT. Интероп-тест проверяет именно это: два разных
назначения видят один и тот же порт сервера. `--no-xudp` — старый способ.

Mux.Cool для TCP сознательно не сделан: Vision-аккаунт у Xray рвёт
Mux-соединения с TCP внутри, а сам Xray как замену мультиплексированию
предлагает xhttp.

### Транспорты, которых нет

`quic` и `h2`/`http` удалены из самого Xray-core — ссылка с ними теперь
даёт ошибку с подсказкой про xhttp. `kcp` (mKCP) — свой надёжный протокол
поверх UDP (~2,5 тыс. строк в Xray, свой контроль перегрузки) — не сделан:
редкий и заметный транспорт, объём несоразмерен пользе.

### Windows

`scripts/cross_windows.sh`: `x86_64-pc-windows-gnu` через mingw-w64.
Стандартную библиотеку Rust для Windows-цели с `static.rust-lang.org`
отсюда по-прежнему не скачать, поэтому она собирается из исходников
(`-Zbuild-std`; исходники `library/` той же версии — через git с GitHub).
Проверка под Wine 9: все 92 теста workspace'а и smoke против Xray-core тем
самым `.exe` (REALITY + Vision с прямой передачей, XUDP) — проходят.
`.exe` зависит только от системных DLL. Шаг добавлен в `scripts/ci.sh`.
На настоящей Windows не запускался.

## Модель угроз: злоумышленник в той же Wi-Fi сети (2026-09-26)

Запрос: «встань на место злоумышленника, подключённого к моей Wi-Fi, —
что он может получить и как это исправить». Разбор по коду (без
отдельного инструментария для атак), защита проверена тестами.

Не может (проверено тестами):
- перехватить или подменить соединение с сервером при `reality`/`tls`:
  чужой сертификат — обрыв рукопожатия до отправки UUID
  (`reality_browser_fallback.rs`: REALITY с недоверенным сертификатом,
  REALITY с настоящим сайтом — «браузерный» визит без UUID, TLS с
  недоверенным сертификатом); TLS 1.2 и возобновление сессий для
  REALITY исключены;
- подключиться к прокси по умолчанию (только `127.0.0.1`; UDP-сокет
  ассоциации — на том же адресе).

Мог — исправлено:
- `security=none`: UUID и трафик открытым текстом, подмена DNS/ARP даёт
  полный перехват → клиент не запускает такую ссылку без
  `--allow-insecure` (проверка в smoke).
- Прокси в сеть: подбор пароля (раньше — до 512 попыток параллельно с
  паузой 0,5 с) → блокировка адреса после 5 ошибок (60 с, удвоение до
  часа, память ограничена 4096 адресами), минимальная длина пароля 12,
  `--allow-ip` (адреса/подсети), предупреждение при запуске
  (`bin/client/src/access.rs`, юнит-тесты; блокировка проверена в smoke).
- Файл с секретом, доступный другим пользователям (Unix) → предупреждение.

Не исправимо на стороне клиента (документировано в README):
SOCKS5 сам по себе не шифрует пароль, адреса и данные между устройством и
компьютером; наблюдатель видит IP сервера, объём и время трафика;
программы без настроенного прокси и DNS браузера без «DNS через SOCKS»
идут мимо туннеля.

Xray-core 26.9.9, три прогона, 8 x 16 МиБ: память на холостом ходу 6,3 МиБ
против 30,4, пик 8,9 против 35,3; пропускная 625 против 572 МиБ/с и до
первого байта 25,4 против 35,8 мс — обе в пределах разброса между

## Устойчивость открытия соединения (2026-09-25)

Аудит кода на предмет того, чего в клиенте не было совсем. Найдено и
исправлено четыре пробела, все — обычная надёжность сетевого клиента:

1. **Нигде не было таймаутов.** Сервер, который принял TCP и молчит
   (типичное поведение заблокированного или зависшего узла), держал бы
   соединение вечно вместе с его задачей и буферами. Добавлены таймауты
   на разрешение имени (5 с), на TCP-подключение (10 с), на TLS/REALITY-
   рукопожатие (15 с) и общий потолок на открытие соединения (30 с).
   Отдельный таймаут именно на рукопожатие нужен потому, что TCP к тому
   моменту уже установлен и его таймаут не срабатывает — это поймал
   тест, первая версия исправления без него всё ещё висела.
2. **Брался только первый адрес** из разрешения имени. Домен часто
   отдаёт и IPv6, и IPv4; если IPv6 в сети не работает (обычное дело),
   клиент не подключался вообще, хотя рабочий IPv4 был в том же ответе.
   Теперь перебираются все адреса по очереди.
3. **Разрешение имени было блокирующим** (`to_socket_addrs`) прямо
   внутри async-кода. Рабочих потоков у tokio по числу ядер (на слабой
   машине два), и один медленный ответ DNS останавливал обработку всех
   соединений. Заменено на асинхронный `tokio::net::lookup_host`.
4. **Не было `TCP_NODELAY` на локальном сокете** к приложению (на
   исходящем он уже стоял).

Плюс понятные сообщения об ошибках: неразрешимое имя теперь даёт
«не удалось разрешить имя <имя>: …», а не системную строку на английском.

Новый тест `core/tests/connect_robustness.rs` (3 теста) проверяет
именно это поведение: молчащий сервер обрывается за 15 с вместо
бесконечного ожидания, мёртвый порт даёт ошибку, а не зависание,
неразрешимое имя даёт понятную ошибку с названием имени. Всего тестов
стало 61.

## Этапы 2 и 8 — закрыты (2026-09-25)

### Этап 2 — проверка работы с памятью (valgrind вместо miri)

`cargo miri` требует nightly-канал Rust, недоступный из этой среды. Взят
**valgrind/memcheck** на обычном stable: он не видит нарушений правил Rust
(aliasing, UB без реального некорректного доступа), которые ловит miri, но
ловит настоящие ошибки доступа к памяти во всём процессе, включая C-код
`aws-lc` (криптография TLS), куда miri вообще не заглядывает.

Прогнано под memcheck:
- 44 юнит-теста — **0 ошибок доступа**;
- 14 интеграционных (настоящие TLS/REALITY/WS/gRPC на loopback) — **0**;
- 4 интероп-теста против Go-сервера REALITY — **0**;
- release-бинарник на живом трафике: 20 соединений подряд через
  SOCKS5 → REALITY → VLESS, 1,25 МБ данных — **0 ошибок доступа,
  0 "definitely lost"**.

Утечек на соединение нет: «possibly lost» одинаков для 1 и для 20
соединений (1 279 байт в 18 блоках) — это разовые выделения при старте
(пулы потоков tokio, инициализация aws-lc), а не рост на каждое соединение.

`scripts/smoke_e2e.sh` научился запускать клиент под обёрткой:
`CLIENT_WRAPPER="valgrind ..." SMOKE_CONNECTIONS=20 scripts/smoke_e2e.sh`.

### Этап 8 — сравнение с настоящим Xray-core

Раньше считался невыполнимым отсюда («нет сети, чтобы поставить Xray-core»).
Оказалось, официальный релизный бинарник с GitHub скачивается

**Попутная проверка:** настоящий клиент Xray-core успешно ходит через наш

оба клиента ходят на один и тот же сервер с одинаковой ссылкой, нагрузку

|---|---|---|---|
| холостой RSS | **5,5 МиБ** | 29,2 МиБ | в 5,3 раза меньше |
| пик RSS под нагрузкой | **8,6 МиБ** | 33,7 МиБ | в 3,9 раза меньше |

### Медленное рукопожатие: причина найдена и устранена

Первый замер показал отставание по времени подключения в 6-21 раз. Разбор:

1. **Это не цена каждого соединения.** 50 подключений подряд заняли 88 мс,
   то есть по 1,8 мс. Но самое первое — 36 мс. Все последующие — 1,6-3 мс.
   Значит, разовая инициализация, а не работа на каждое соединение.
2. **Это не наш код.** Процессорное время клиента на подключениях со
   второго и дальше — ниже порога измерения (0 мс на 50 подключений).
3. **Виновник — засев генератора случайных чисел в aws-lc.** Пробник
   `bench/src/bin/warmup_probe.rs` (запускать в отдельных процессах —
   разовое на то и разовое):

   | действие | время |
   |---|---|
   | установка crypto-провайдера rustls | 0,00 мс |
   | **первая генерация ключа обмена** | **26-32 мс** |
   | последующие генерации (среднее из 20) | 0,02 мс |

   Цена одинакова для X25519, secp256r1 и X25519MLKEM768 — значит, дело
   не в постквантовой группе. Решающий опыт: если в том же процессе
   сначала запросить случайные байты, а ключ генерировать после, цена
   переезжает на них: **случайные байты 28,08 мс, генерация ключа 0,08 мс.**
   То есть aws-lc засевает свой ГСЧ лениво, при первом запросе случайных
   байт (сбор энтропии по дрожанию таймингов процессора), и это стоит
   ~28 мс один раз на процесс.

**Исправление** (`transport::tcp_tls::ensure_crypto_provider` +
вызов при старте в `bin/client/src/main.rs`): один запрос случайных байт
при инициализации, до начала приёма соединений. Байты никуда не идут,
нужен только побочный эффект — засев. Разовая цена переехала со первого
соединения пользователя на старт процесса, где её никто не ждёт.

Было / стало (8 соединений x 16 МиБ, тот же стенд):

| | было | стало | Xray-core |
|---|---|---|---|
| рукопожатие, медиана | 70 мс | **15,8 мс** | 5,3 мс |
| первое соединение | 36 мс | **5,7-8,7 мс** | — |

### ⚠️→✅ Поправка: «отставание по рукопожатию» было ошибкой замера

Задача «догнать Xray по времени подключения» привела к разбору, который
показал, что сравнивались **разные вещи**.

Замерялось время до ответа на SOCKS5 CONNECT. Оказалось, что
**Xray-core отвечает на него авансом, не дожидаясь соединения с
сервером.** Проверено прямо: если направить Xray на порт, где сервера
нет вообще, он всё равно отвечает «успех» за 2,8 мс. Этот клиент
отвечает только после настоящего рукопожатия (TCP + TLS + REALITY +
VLESS), то есть честно сообщает о неудаче, если сервер недоступен.

Честный показатель — **время до первого байта данных, прошедшего через
туннель**: он включает полный путь у обоих. По нему (30 последовательных
соединений):

| | до ответа SOCKS5 | до первого байта данных |
|---|---|---|
| reality-core | 1,74 мс | **1,93 мс** |
| Xray-core | 0,17 мс | 2,56 мс |

То есть «в 3 раза медленнее» не было: при одинаковой мерке этот клиент
оказался даже чуть быстрее. `scripts/stage8_loadgen.py` исправлен — он
меряет время до первого байта, а ответ на CONNECT печатает с пометкой,
что он между клиентами не сравним.

Разница в поведении реальная и осознанная: ответ авансом выглядит
быстрее, но приложение считает соединение установленным даже когда
сервер недоступен. Мы сообщаем об ошибке сразу.

### Итоговое сравнение по трём прогонам (честная мерка)

Один прогон вводил в заблуждение: разброс между прогонами оказался
сопоставим с разницей между клиентами. Три прогона, 8 соединений x 16 МиБ:

| показатель | reality-core | Xray-core | вывод |
|---|---|---|---|
| память на холостом ходу, МиБ | **5,9** | 29,5 | мы лучше в 5,0x, разница реальная |
| пик памяти, МиБ | **8,7** | 34,3 | мы лучше в 3,9x, разница реальная |
| до первого байта данных, мс | 17,1 | 22,6 | ничья (разница меньше разброса) |
| пропускная, МиБ/с | 985 | 966 | ничья (разница меньше разброса) |

**Итог: клиент не уступает Xray-core ни по одному показателю** — две
победы по памяти и две ничьи. Прежние выводы «на 19 % медленнее» и «в 3
раза дольше подключается» оба оказались артефактами замеров: первый —
шумом одного прогона, второй — сравнением разных величин.

Что осталось из настоящего: первое соединение после запуска ~6 мс против
~2 мс у последующих — прогрев кода рукопожатия при первом проходе.
Мелочь по сравнению с прежними 36 мс, и на реальной сети, где только
круговая задержка до сервера обычно десятки миллисекунд, почти незаметна.

Побочное наблюдение из разбора: на рукопожатие наш клиент тратит **меньше**
процессорного времени, чем Xray (0,70 мс против 0,95 мс), — замерено
напрямую по `/proc/<pid>/stat` на 200 последовательных соединениях.

### Находка 1 (критично): `flow=xtls-rprx-vision` не поддерживается — и молча игнорируется

`vless/uri.rs` читает `flow=` из ссылки, но дальше это поле нигде не
используется: запрос VLESS всегда уходит с пустыми addons. По исходнику
сервера (`inbound.go`, ~стр. 593) аккаунт с `flow = xtls-rprx-vision`
на TCP-запрос с пустым flow отвечает отказом: *"rejected since the
client flow is empty"*. А VLESS + Vision + REALITY поверх TCP — именно та
конфигурация, которую рекомендует документация Xray и которая стоит в
большинстве реальных ссылок. То есть с типичным сервером этот клиент
сейчас **не подключится вообще**, а в логе клиента не будет понятной
причины. Раньше это нигде в плане не было отмечено — пробел, не решение.

### Находка 2 (хорошая): интероп-тест с настоящей серверной реализацией, возможно, достижим прямо здесь

`proxy.golang.org` и `static.rust-lang.org` закрыты (403), но
`git` по `https://github.com` работает, и в песочнице есть Go 1.24.7.
`XTLS/REALITY` — это Go-библиотека (не только часть Xray-core), и её
зависимости почти все живут на GitHub. Модули `golang.org/x/*` можно
взять из зеркал `github.com/golang/{crypto,sys,...}` через
`replace ... => ./локальный-клон`. Препятствие: `go.mod` у REALITY
требует `go 1.27`, в песочнице 1.24 — надо проверить, собирается ли
библиотека с понижённой директивой, или собрать Go 1.27 из
`github.com/golang/go` (bootstrap от 1.24). Если получится, Этап 5
перестаёт быть заблокированным целиком: минимальный Go-сервер на
`reality.Server` + эхо после рукопожатия даёт настоящий
сторонний REALITY-сервер для проверки AuthKey/SessionId, X25519MLKEM768,
HMAC-сертификата и GREASE. Ревью человеком это не заменяет, но
"самопроверку против собственной реализации сервера" заменяет.

### Ход выполнения

- ✅ **Шаг 1** — `flow=` разбирается в `vless::Flow`. Неизвестное значение даёт
  ошибку разбора, `xtls-rprx-vision` даёт явную ошибку «не поддерживается»
  при старте клиента и перед каждым соединением
  (`VlessConfig::ensure_flow_supported`). Молчаливого пустого flow больше нет.
- ✅ **Шаг 1б (найден по ходу, критично)** — дедлок с текущим Xray-сервером.
  Сервер (`inbound.go`: `EncodeResponseHeader` + `SetFlushNext`) отправляет
  заголовок ответа VLESS только вместе с первыми данными от цели, а клиент
  ждал этот заголовок до отправки чего-либо. Для HTTPS/HTTP, где первым
  говорит клиент, это взаимная блокировка на каждом соединении. Наши
  тестовые серверы отвечали заголовком сразу, поэтому тесты этого не
  видели. Исправлено: `vless_handshake` заменён на `vless_connect` — запрос
  уходит сразу, а заголовок ответа снимается лениво при первом чтении
  (`VlessStream`). Регрессионный тест воспроизводит поведение
  `SetFlushNext`. 58 тестов, clippy чисто.

- ✅ **Шаг 2 — интероп-стенд работает.** Go 1.27.1 собран из исходников
  (`github.com/golang/go`, bootstrap от установленного 1.24.7), зависимости
  `github.com/xtls/reality` склонированы по git, `golang.org/x/*` взяты из

  настоящая библиотека REALITY плюс Go `crypto/tls` в роли сайта-приманки плюс

  `SetFlushNext` у Xray). Тест `core/tests/interop_go_reality.rs` (4 теста,

### Готово в эту сессию

- **Этап 3 (частично, три сессии подряд):** `core/src/fingerprint/chrome_profile.rs` —

## Этап 2 — Оптимизация памяти на конкуренции
- Буфер закрепляется за соединением целиком, не за пакетом; не глобальный shared pool.
- ⚠️ **Крипто-ошибки не прощают:** уже на этом этапе, если буферный код где-то пересекается с областью, где позже будет расшифрованный трафик (Этап 5+), любая логическая ошибка в работе с памятью (use-after-free, переиспользование буфера с чужими данными) — это не просто краш, а потенциальная утечка данных между сессиями. Закладывать `cargo miri`/sanitizers в тесты этого этапа, а не только на финале.

**Реализовано:** `core/src/relay.rs` — каждое направление копирования получает свой `Vec<u8>`, выделенный один раз при старте соединения (`copy_bidirectional_with_buffer_size`) и живущий до его конца; никакого глобального пула, никакой per-packet аллокации. Потоки разбиваются на read/write-половины через `tokio::io::split` (проверенный примитив tokio), а не через самописный poll-based state machine — сознательно не переизобретали то, что уже надёжно решено (см. риск "соло против комьюнити" в Этапе 4, применённый здесь заранее).

⚠️ **Не выполнено — требует действия пользователя в своей среде:** `cargo miri` не удалось поставить в этой песочнице — nightly-канал качается с `static.rust-lang.org`, а исходящий доступ здесь ограничен только реестром crates.io (прокси не пропускает остальное). У себя локально: `rustup toolchain install nightly --component miri`, затем `cargo +nightly miri test -p reality-core --lib`. Это накроет `relay::tests`, `socks5::tests`, `vless::protocol::tests` — все они на `tokio::io::duplex` (чистый in-memory канал), с которым miri справляется. Тест `core/tests/tls_loopback.rs` использует настоящие TCP-сокеты и TLS — под miri не запустится в принципе (miri не умеет в реальные сетевые syscalls), его отдельно стоит гонять под ASan/TSan (`RUSTFLAGS="-Z sanitizer=address" cargo +nightly test -p reality-core --test tls_loopback`) на nightly же. Ни то, ни другое не сделано за пользователя — сделать до того, как в буферный код Этапа 5 начнёт попадать расшифрованный трафик.

## Этап 3 — TLS-фингерпринтинг (uTLS-эквивалент)
- ClientHello-эмуляция под браузеры, сверка JA3/JA4.
- ⚠️ **Это не разовая задача, а процесс:** браузеры меняют fingerprint несколько раз в год — заложить регулярный мониторинг и обновление дампов ClientHello как постоянную статью работ, не как "сделали и забыли".
- ⚠️ **Гонка с DPI:** даже идеально повторённый fingerprint браузера сегодня не гарантирует, что DPI не научится отличать его иным способом (тайминги, TCP-стек) завтра. План должен предполагать возврат к этому этапу многократно, а не один раз.

**Реализовано (измерение):** `core/src/fingerprint/` — парсер сырых байт TLS ClientHello (`client_hello.rs`), JA3 (`ja3.rs`) и JA4 (`ja4.rs`), формулы обоих перепроверены в тестах против опубликованных эталонных примеров (JA3 — независимый разбор с md5, JA4 — рабочий пример из технического описания FoxIO, оба совпали побайтово при независимой проверке через `python3 -c "import hashlib; ..."` до того, как попасть в тест). `capture.rs` перехватывает сырые байты ClientHello прямо на сокете (rustls их не отдаёт) — `transport::connect_tls_capturing_client_hello`. Практический инструмент: `cargo run -p fpcheck -- --server '<vless-ссылка>'` — печатает JA3/JA4/поля ClientHello для *реального* текущего соединения.

⚠️→🟡 **Поправка (сессия "составь план и действуй"): предыдущая формулировка про rustls была неточной, опровергнута эмпирически, не тихо исправлена.** Раньше здесь было написано, что "rustls принципиально не даёт управлять порядком cipher suites/extensions" и что фингерпринт клиента "стабильный, но не браузерный". Проверено заново, построчно и эмпирически (не по памяти):

- **Порядок cipher suites управляем публично**, без всякого патча — `rustls::crypto::CryptoProvider::cipher_suites` обычный `pub Vec`, сохраняющий порядок при кодировании в ClientHello (`client/hs.rs`, `let mut cipher_suites: Vec<_> = config.provider.cipher_suites.iter()...`). Реализовано: `core/src/fingerprint/chrome_profile.rs` — эталон порядка взят напрямую из `refraction-networking/utls` (та самая зависимость REALITY-клиента в Xray-core, см. Этап 5), файл `u_parrots.go`, профиль `HelloChrome_133` (`curl raw.githubusercontent.com`, не по памяти). Эталон Chrome — 16 suite'ов (GREASE + 3×TLS1.3 + 6×TLS1.2-ECDHE + 6×TLS1.2-legacy-RSA/CBC); наш провайдер (`aws-lc-rs`) реализует только первые 9 (три TLS1.3 + шесть ECDHE) — CBC/голый-RSA не реализованы НИ В ОДНОМ современном rustls-провайдере намеренно (это небезопасные механизмы), реализовывать их заново только ради байт-в-байт совпадения фингерпринта означало бы тащить небезопасную криптографию ради маскировки — сознательно не сделано, см. докстринг `chrome_profile.rs`. Devять доступных suite'ов теперь идут в том же относительном порядке, что и у Chrome; подключено в `transport::tcp_tls` (`build_client_config` и REALITY-путь) — действует на всех TCP-based транспортах (TCP/WS/gRPC), для REALITY и обычного TLS одинаково. Проверено ТРОЙНО: юнит-тест на функцию переупорядочивания; юнит-тест на защиту от "потерять" suite, которого нет в списке Chrome; и живой TCP+TLS-хендшейк на loopback с перехватом сырых байт провода и разбором их тем же независимым парсером, что и `fpcheck` — итоговый порядок на проводе (`1301 1302 1303 c02b c02f c02c c030 cca9 cca8`) байт-в-байт совпал с ожидаемым.
- **Порядок TLS-расширений НЕ статичен** — вендоренный rustls САМ рандомизирует его на каждое соединение (`ClientHelloDetails::extension_order_seed`, генерируется `crate::rand::random_u16(...)` при каждом новом `ClientHelloInput::new`, применяется в `emit_client_hello_for_retry` через `exts.order_seed`). Проверено эмпирически прямо в этой сессии: три реальных TCP+TLS1.3-рукопожатия на loopback дали три РАЗНЫХ порядка одного и того же набора из 10 расширений. Это, по счастливому совпадению, ровно то, что делает и сам Chrome 106+ (`ShuffleChromeTLSExtensions` в том же `u_parrots.go` — тоже перемешивает большинство расширений на каждое соединение, что и стало исходной причиной изобретения JA4 поверх JA3: JA3 хэширует расширения как есть, порядко-чувствительно, JA4 — предварительно сортирует их именно из-за такого шаффлинга у современных браузеров). Значит патчить rustls ради порядка расширений не нужно — он уже недетерминирован тем же способом, что и у Chrome.

**Что по-прежнему не сделано — теперь куда более узкий остаток, не архитектурная развилка целиком:**
⚠️→✅ **GREASE (RFC 8701) — cipher suite сделан ("выполняй все пункты по порядку", первая правка).** Ни `aws-lc-rs`, ни сам rustls общего GREASE не умели (только ECH-специфичный, `client/hs.rs`) — потребовался патч, но узкий и низкорисковый: в `vendor/rustls-reality-patch/src/client/hs.rs`, там же, где уже строится `cipher_suites: Vec<CipherSuite>` для REALITY, теперь ещё и вставляется `CipherSuite::Unknown(..)` со случайным GREASE-нибблом первым элементом (используется тот же `crate::rand::random_u16`, что и для `extension_order_seed` — не новый источник случайности). Безопасно и для REALITY, и для обычного TLS: выбор cipher suite не участвует ни в key_share, ни в named_groups, ни в HRR-логике REALITY (см. подробное обоснование в докстринге `chrome_profile.rs`). Проверено живым TCP+TLS1.3-хендшейком на loopback (`core/tests/fingerprint_chrome_profile.rs`) — рукопожатие проходит (обязано по RFC 8701), первый suite на проводе реально GREASE-формы, порядок остальных — Chrome 133 (см. выше).

⚠️→✅ **GREASE доведён до конца — все места, где его ставит Chrome, все пути (включая REALITY).** Ground truth заново сверен напрямую (`u_parrots.go` utls: профиль `HelloChrome_133` и функция `ApplyPreset`, где плейсхолдеры заменяются реальными значениями): у Chrome пять независимых GREASE-значений на соединение (раскладка BoringSSL `ssl_grease_index_t`) — первый cipher suite; первая группа в `supported_groups` и она же первой записью `key_share` с телом `[0]`; первая версия в `supported_versions`; два отдельных GREASE-расширения — самое первое в списке с пустым телом и самое последнее с телом `[0]`, типы гарантированно разные (при совпадении второй `^= 0x1010`). Реализация (`vendor/rustls-reality-patch`):
- `client/common.rs` — `GreaseValues`, генерируется один раз в `ClientHelloInput::new` рядом с уже существующим `extension_order_seed` и по той же причине: второй ClientHello после HelloRetryRequest должен нести те же значения, что и первый (у utls/BoringSSL — `greaseSeed` на соединении). Прежнее поле `named_group_grease_seed` и генерация GREASE-cipher заново на каждый hello — заменены этим.
- `client/hs.rs` — GREASE первым в cipher suites, named_groups, key_share, supported_versions.
- `msgs/handshake.rs` — `SupportedProtocolVersions.grease` (только на отправку) и `ClientExtensions.grease_extensions`: два GREASE-расширения пишутся прямо в `ClientExtensions::encode` — первым и последним, но строго перед `pre_shared_key` (RFC 8446 §4.2.11). **Правка макроса `extension_struct!`, которой раньше опасались, не понадобилась**: `encode` написан вручную, а длину списка и так считает `LengthPrefixedBuffer` — ни ручного пересчёта length-префикса, ни сырых байт поверх готового ClientHello. Прежняя оценка "нужна правка макроса или сырые байты" была завышена. В `collect_used()`/`sent_extensions` GREASE не попадает — сервер и не должен его "отвечать".

⚠️ **Найден и исправлен баг предыдущей итерации.** После HelloRetryRequest, указавшего группу, RFC 8446 §4.1.2 требует key_share ровно из ОДНОЙ записи. Первая версия GREASE-патча добавляла GREASE-запись и туда: во втором hello уходило `[GREASE, secp256r1]`. Сервер rustls это молча терпел, поэтому ни один тест не падал; Go `crypto/tls` (а значит, и серверная часть REALITY — `len(clientHello.keyShares) != 1` в `handshake_server_tls13.go`) рвёт такое соединение. Поймано новым тестом `hello_retry_request_path_still_completes_with_grease` (сервер поддерживает только secp256r1 → гарантированный HRR, разбираются ОБА ClientHello с провода); исправлено тем же условием, что у "бесплатной" второй записи key_share в rustls. Урок для остальной работы: снисходительность тестового сервера не доказывает корректность — проверять надо байты на проводе против текста RFC, а не "хендшейк прошёл".

⚠️→✅ **Поправка: GREASE в группах/key_share для REALITY — больше не отложен.** Раньше он был сознательно отложен "до интероп-теста против живого сервера", потому что касается той же машинерии, что анти-HRR-трюк REALITY. Пересмотрено по исходникам (curl `raw.githubusercontent.com`), а не по предположениям:
1. Сервер `XTLS/REALITY` (`tls.go`, цикл по `hs.clientHello.keyShares`) неизвестную группу в key_share просто пропускает — ни одна ветка на неё не срабатывает.
2. После аутентификации группа берётся из ServerHello сайта-приманки, которому REALITY пересылает наш ClientHello как есть; GREASE-группу такой сервер не знает и при выборе не учитывает (RFC 8701; и каждый Chrome в мире шлёт ему то же самое). Реальная группа у нас по-прежнему одна — `X25519MLKEM768`, так что повода для HRR не прибавилось.
3. Главное: собственный REALITY-клиент Xray-core (`transport/internet/reality/reality.go`) — это `utls.UClient` с отпечатком из `tls.GetFingerprint`, по умолчанию `HelloChrome_Auto` = `HelloChrome_133`. То есть REALITY-серверы в production штатно получают ровно эти GREASE-значения во всех пяти местах.
4. И наоборот: GREASE в cipher suites при его отсутствии в группах/версиях/расширениях — сочетание, которого нет ни у одного браузера, само по себе примета.
Проверено `reality_handshake.rs`: на проводе GREASE во всех пяти местах, единственная реальная группа — X25519MLKEM768, и независимая AEAD-проверка SessionId проходит — то есть GREASE-байты вошли в AAD ровно так же, как их посчитал клиент. Живого интероп-теста это по-прежнему не заменяет (см. Этап 5), но это касается REALITY целиком, не GREASE отдельно.
- **Набор и значения самих расширений** (не порядок и не GREASE) — signature_algorithms, ALPN, сжатие сертификатов, ALPS, SCT, ECH-GREASE — не сверены построчно с Chrome. Список групп для НЕ-REALITY пути уже совпадает (`X25519MLKEM768, X25519, secp256r1, secp384r1` — то, что по умолчанию отдаёт `aws-lc-rs`); прежняя формулировка "`X25519MLKEM768` первой — только для REALITY" была неверна.
- **`craftls`/`boring` как способ добрать оставшееся** — если после полного набора расширений (через продолжение того же небольшого патча, что уже используется для REALITY — НЕ через смену крипто-бэкенда) всё ещё останется зазор, тогда встаёт первоначальный вопрос: `craftls` ([github.com/3andne/craftls](https://github.com/3andne/craftls), не оценён на зрелость) или FFI на BoringSSL (крейт `boring`). Открытые issue rustls/rustls#1421/#1932/#2498, на которые раньше ссылались как на доказательство "rustls принципиально не умеет" — не перепроверялись заново в эту сессию и могли устареть (см. правку выше — по факту часть того, что они описывали, уже не актуальна для этой версии). Решение по этому крайнему случаю по-прежнему не принято за пользователя, но теперь это куда менее вероятно понадобится, чем казалось раньше.

## Этап 4 — Транспорты (WebSocket, gRPC)
- Использовать готовые библиотеки (tokio-tungstenite, h2), переписывать вручную только при доказанном профилированием оверхеде.
- ⚠️ **Соло против комьюнити:** готовые библиотеки тут выбраны отчасти потому, что баг в самописном фреймере некому будет быстро выловить кроме вас — в отличие от Xray, где это делают тысячи установок. Не экономить на этом этапе ради памяти ценой рискованного самодельного кода.

**Реализовано:**
- `core/src/transport/ws.rs` — WebSocket поверх TLS через `async-tungstenite` + `ws_stream_tungstenite` (сам WS-фреймер не писали). Проверено сквозным тестом на настоящем TCP+TLS+WS до собственного тестового сервера (`core/tests/ws_loopback.rs`).
- `core/src/transport/grpc.rs` — один bidi-стрим gRPC ("gun"-режим Xray-core/V2Ray, без мультиплексирования) через `h2` напрямую; сами написали только тонкий слой protobuf-varint и gRPC-кадрирования поверх него (путь `/{serviceName}/Tun`, кадр = 1 байт флага сжатия + 4 байта BE-длины + protobuf `Hunk{bytes data=1}` — формат перепроверен по двум независимым техническим источникам, не придуман). Проверено сквозным тестом на настоящем TCP+TLS(ALPN h2)+HTTP/2 до собственного тестового h2-сервера (`core/tests/grpc_loopback.rs`) — **этот тест поймал реальный дедлок** (сервер не двигал `h2::server::Connection` в фоне, из-за чего `RecvStream::data().await` вис навсегда; исправлено).
- `bin/client` теперь выбирает транспорт по `type=` в ссылке (`tcp`/`ws`/`grpc`) автоматически.

⚠️ **Не проверено на реальном Xray-core/V2Ray сервере** — такого сервера в этой среде нет и не может быть (сеть ограничена реестром crates.io). gRPC-кадрирование выверено по документации/исходникам, а не по факту "подключился и заработало" к чужой реализации — сверить с реальным сервером до боевого использования. Флоу-контроль на отправку в gRPC сделан по упрощённой схеме (`send_data` напрямую, без `reserve_capacity`/`poll_capacity`) — см. предупреждение в `transport/grpc.rs`: при по-настоящему медленном получателе `h2` будет буферизовать без ограничения по памяти.

## Этап 5 — REALITY
- X25519, ручная сборка ClientHello-полей, fuzz-тестирование, локальный сервер для отладки + матрица совместимости с реальными версиями Xray-server.
- ⚠️ **Крипто-ошибки не прощают (ключевая точка риска всего проекта):** это самый опасный этап — ошибка здесь не ломает функциональность, а молча снижает анонимность. По возможности — привлечь стороннего человека с криптографическим бэкграундом для ревью хотя бы этой части, даже если остальной код пишется соло.
- ⚠️ **Юридический риск:** реализация обхода активного пробинга — именно то, что подпадает под регулирование средств обхода блокировок. Оценить юридические последствия разработки/публикации до начала этого этапа, не после.

**Статус по двум пунктам риска выше, прежде чем читать дальше про реализацию:**
юридический риск пользователь оценил сам, явно ("юридическую часть я уже прикинул") — это его собственная оценка, не моя, и я не могу её ни подтвердить, ни оспорить. **Крипто-ревью по-прежнему не проводилось** — про него разговора не было, и я сам его заменить не могу: я перепроверял формулы против первоисточников и тестовых векторов (см. ниже), но это не замена независимому ревью, которое план требует "до начала, не после". Двигаюсь дальше по прямому указанию пользователя, но этот пункт держу открытым, а не закрытым явочным порядком.

**Реализовано (`core/src/reality/`):**
- `auth.rs` — X25519 ECDH (`x25519-dalek`), вывод AuthKey через HKDF-SHA256 (соль = `ClientHello.random[..20]`, info = `"REALITY"`), сборка/шифрование поля SessionId через AES-256-GCM (nonce = `random[20..32]`, AAD = весь ClientHello целиком) и HMAC-SHA512-проверка сертификата (`verify_ed25519_hmac`). Байт-в-байт сверено с двумя независимыми источниками (клиентский `Seal` в `XTLS/Xray-core`, `transport/internet/reality/reality.go`, и симметричный серверный `Open` в `XTLS/REALITY`, `tls.go`) — оба независимо цитируют одни и те же salt/info/nonce/AAD, что и разрешило неоднозначность, замеченную на этапе исследования (открытый plaintext-блок перед AEAD — 16 байт: версия(3)+reserved(1)+timestamp(4)+short_id(8), а не 24, как можно было прочитать по одному источнику — 16-байтный AES-GCM-тег ровно дополняет их до 32 байт SessionId).
- Тесты: официальный тестовый вектор X25519 из RFC 7748 §6.1 (Alice/Bob) — перепроверен самостоятельно через `cryptography` на Python до того, как попасть в Rust-тест (та же дисциплина, что и для JA3/JA4 в Этапе 3); раунд-трип seal/open, где расшифровка сделана независимой функцией, а не тем же кодом, что шифровал; отдельный тест на то, что подмена AAD ломает AEAD-проверку; позитивные и негативные тесты на HMAC.
- `verifier.rs` — `rustls::client::danger::ServerCertVerifier`, который заменяет проверку цепочки доверия X.509 на HMAC-SHA512-проверку из `auth.rs` (это именно то, что делает `VerifyPeerCertificate` в Xray-core), но НЕ ослабляет остальной TLS 1.3: подписи `Certificate`/`CertificateVerify` по-прежнему проверяются по-настоящему через `rustls::crypto::verify_tls13_signature` с тем же провайдером, которым TLS вообще пользуется — заменён только источник доверия к ключу, не рукопожатие целиком. Протестировано против сертификатов, собранных `rcgen` с вручную переписанным полем подписи на HMAC-значение (только так и можно сымитировать REALITY-сертификат без живого REALITY-сервера) — принимает верный HMAC, отвергает чужой ключ и отвергает настоящую (не-HMAC) Ed25519-подпись.
- `vless/uri.rs::VlessConfig::reality_params()` — разбор `pbk=` (base64url X25519-ключ сервера) и `sid=` (hex ShortId) из ссылки.

**Поправка по ходу решения архитектурного вопроса ниже:** раньше здесь было утверждение, что `refraction-networking/utls` (реальная зависимость REALITY-клиента в Xray-core) идёт по пути "FFI на BoringSSL" — это было неверно, найдено при дальнейшем исследовании и оставлено здесь как пример собственной ошибки, а не тихо исправлено. По факту: `refraction-networking/utls` — это форк *стандартной библиотеки Go* (`crypto/tls`), с прямым доступом к полям структуры ClientHello, а не обёртка над BoringSSL. Ниже — решение с учётом этой поправки.

**Архитектурный вопрос TLS-бэкенда — решён, минимальным патчем rustls, без смены крипто-бэкенда целиком:**
Три независимых существующих Rust-реализации REALITY (`jacek4yang/rust-reality`, `aimalygin/xray-rust` с собственным патчем `shaped-rustls`, `undead-undead/xray-lite` с директорией `rustls-reality`) — все независимо выбрали патч rustls, ни одна не пошла через `boring`/BoringSSL. `boring` — реальный, проверенный в проде путь (на нём стоит `rquest`/`wreq`, HTTP-клиенты для JA3/JA4-эмуляции браузера, используя нативную функцию самого BoringSSL `SSL_CTX_set_permute_extensions`), но это решает Этап 3, не Этап 5 — публичный API BoringSSL так же не даёт установить произвольный `legacy_session_id` вне механизма resumption, как и rustls, а патчить сам BoringSSL (C, не Rust) тяжелее, чем патчить rustls.

Вместо того чтобы форкать весь конвейер сборки ClientHello (как `craftls`, см. Этап 3 — 27 звёзд, статус "under active development", нестабильный API) — нашёлся путь МЕНЬШЕ: `rustls` уже публично (без всякого форка) даёt подключить свой `ClientSessionStore` (`ClientConfig::resumption`). Если он вернёт для TLS1.2 фейковую "сессию для резюмирования" с нужным нам `SessionId`, а тикет у неё пустой, то по коду `client/hs.rs` (прочитано построчно): (а) `ClientHelloInput::new()` берёт `session_id` именно из этой сессии и подставляет его в исходящий ClientHello как есть, не перегенерируя случайным, и (б) `prepare_resumption` ничего лишнего не добавляет в расширения, если конфиг явно ограничен TLS1.3 (без TLS1.2 в списке поддерживаемых версий). Проблема была только в том, что сам тип `Tls12ClientSessionValue` и его конструктор, и сам тип `SessionId` — были `pub(crate)`, ненаходимы снаружи крейта.

**Патч:** `vendor/rustls-reality-patch/` — полная копия исходников rustls 0.23.45 с ТРЕМЯ точечными правками видимости, ни одна не трогает существующую логику:
1. `msgs/handshake.rs`: `SessionId` стал `pub` + новый метод `SessionId::from_bytes_public(data: &[u8])`.
2. `msgs/persist.rs`: `Tls12ClientSessionValue::new(...)` стал `pub` (было `pub(crate)`).
3. `msgs/handshake.rs`: `CertificateChain` стал `pub` + новый метод `CertificateChain::empty()` (нужен как безобидная заглушка — при пустом тикете `server_cert_chain` нигде дальше не читается, проверено по коду).
4. `lib.rs`: добавлены публичные реэкспорты `SessionId`/`CertificateChain` рядом с уже существующим реэкспортом `Tls12ClientSessionValue` в модуле `client` — без реэкспорта тип формально `pub`, но недостижим снаружи.

Подключается как `[patch.crates-io] rustls = { path = "vendor/rustls-reality-patch" }` в корневом `Cargo.toml` — патчит ВСЮ зависимость от `rustls` в графе (включая транзитивную через `tokio-rustls`) одной строкой, версия та же (0.23.45), остальной код изменения не заметил (полный `cargo test --workspace` — без единой правки где-либо кроме этих трёх мест — прошёл как прежде).

**Проверено эмпирически, не только по чтению исходников** (`core/tests/reality_session_id_spike.rs`) — настоящий TCP+TLS1.3 до собственного тестового сервера, с перехватом сырых байт ClientHello (`capture.rs`) и независимым разбором (`fingerprint::parse_record`, который для этого расширен новым полем `ClientHelloInfo::session_id`):
- заданные 32 байта SessionId (`00 01 02 .. 1f`) побайтово доходят до провода — не отбрасываются, не перегенерируются;
- согласованная версия — TLS 1.3 (проверено и на клиенте, и на сервере), никакого незаметного отката на 1.2;
- первый прогон теста реально ловил проблему — обычный `ClientConfig::builder()` (TLS1.2 разрешён по умолчанию) добавлял лишнее расширение `session_ticket` (0x0023) в ClientHello даже с пустым тикетом, просто потому что TLS1.2 в принципе разрешён конфигом; с `ClientConfig::builder_with_protocol_versions(&[&rustls::version::TLS13])` расширение пропадает — фингерпринт ClientHello (Этап 3) остаётся чистым.

**Поправка №2 — спайк выше оказался не тем механизмом для полного REALITY:**
дальнейшее чтение `client/hs.rs` построчно показало, что `ClientSessionStore::tls12_session()` (на котором держится спайк) вызывается ВНУТРИ `ClientHelloInput::new()` ДО того, как генерируется `ClientHello.random` (`random: Random::new(...)` — самая последняя строка той же функции). А AuthKey/nonce/AAD в REALITY зависят именно от `random`, который в момент вызова `tls12_session()` ещё не существует. Плюс сам протокол требует переиспользовать ОДИН эфемерный X25519-секрет дважды — для ECDH с REALITY-сервером (AuthKey) и позже для настоящего TLS1.3 ECDH с сервером из ServerHello — а `ClientSessionStore` вообще не участвует в выборе key_share. Спайк остался в дереве и продолжает проходить (полезен как независимое доказательство первого шага — "патченный rustls МОЖЕТ доставить произвольный SessionId на провод"), но в бою не используется. Это не откат решения — вывод "патчить rustls, не менять TLS-бэкенд целиком" остался верным, поменялась только точка приложения патча внутри rustls.

**Итоговый (боевой) механизм — новый хук `rustls::client::RealityClientHook`:**
вместо `ClientSessionStore` — точечный трейт (3 метода), который патч добавляет в `vendor/rustls-reality-patch/src/client/client_conn.rs`, плюс поле `ClientConfig::reality: Option<Arc<dyn RealityClientHook>>` (по умолчанию `None` — без него ничего не меняется). Патч `client/hs.rs` вызывает его в двух точных местах внутри `emit_client_hello_for_retry` (единственная функция, которая реально строит исходящий ClientHello):

1. В начале функции — если `config.reality` установлен и это не HelloRetryRequest-повтор, key_share подменяется на `RealityKeyExchange` (обёртка вокруг хука вместо обычного `tls13::initial_key_share`) — тот же эфемерный X25519-секрет теперь идёт и в key_share исходящего ClientHello.
2. После того как `chp_payload` (тело ClientHello) полностью собрано (включая обработку ECH) — вызывается `hook.seal_session_id(&input.random.0, &aad)`, где `aad` — реальные сериализованные байты этого самого Handshake-сообщения (тип+длина+тело) с полем SessionId, обнулённым на смещении 39 (то же самое место и тот же приём, что `hello.Raw[39:71]` в `reality.go` Xray-core — сверено построчно с исходником, не угадано: `aead.Seal(hello.SessionId[:0], hello.Random[20:], hello.SessionId[:16], hello.Raw)`). Результат подставляется в `chp_payload.session_id` и (отдельная правка, тоже пойманная эмпирически, см. ниже) в `input.session_id`, чтобы повторный ClientHello на HelloRetryRequest не улетел с обнулённым плейсхолдером вместо реально отправленного значения (RFC 8446 §4.1.2 требует, чтобы `legacy_session_id` совпадал между первым и вторым ClientHello).
3. `RealityKeyExchange::complete()` (вызывается rustls один раз, когда придёт ServerHello с настоящим key_share сервера) делегирует в `hook.complete_real_ecdh(peer_pub_key)` — обычное завершение TLS1.3 ECDH тем же секретом, который уже был использован для AuthKey.

`ClientHelloInput::new()` также патчен — при активном `config.reality` `session_id` всегда стартует с 32 нулевых байт (тот же плейсхолдер, что и AAD выше), а не с обычной логики резюмирования/случайных байт.

Реализация хука — `core/src/reality/hook.rs`, `RealityHook`: `StaticSecret` (не `EphemeralSecret` — намеренно, тот же скаляр нужен дважды), AuthKey кладётся в `OnceLock` при первом вызове `seal_session_id`, читается позже `RealityCertVerifier::from_hook` при проверке сертификата (тот же `Arc<RealityHook>`, что и в `ClientConfig::reality`).

**Найдено эмпирически по ходу, не предсказано заранее:**
1. `PeerMisbehaved(IllegalHelloRetryRequestWithWrongSessionId)` при первом прогоне `reality_handshake.rs` — сервер (обычный rustls-сервер на loopback) легитимно слал HelloRetryRequest, потому что `named_groups`-расширение ClientHello перечисляло полный список групп провайдера (в современных сборках aws-lc-rs первым часто идёт гибридная PQ-группа), а реально предложенный key_share был только X25519 — несоответствие. **Исправлено**: при активном REALITY (и только для самого первого ClientHello) `named_groups` тоже принудительно ограничивается одним `X25519` — список групп обязан совпадать с тем, что реально уходит в key_share.
2. После этого исправления рукопожатие стало проходить, но независимая (написанная отдельно в тесте, не переиспользующая `reality-core`) AEAD-проверка на стороне "сервера" сначала не открывалась — тест брал в AAD "весь остаток перехваченного буфера" вместо ровно одного TLS-рекорда с ClientHello. **Исправлено** в самом тесте (`reality_handshake.rs`): AAD = ровно `record_len` байт handshake-сообщения, взятых по длине из заголовка TLS-рекорда, не всё, что случайно легло в буфер перехвата следом.

**Подтверждено эмпирически** (`core/tests/reality_handshake.rs`, полностью проходит) — не через переиспользование `reality-core`-кода для проверки самого себя, а независимо написанными в тесте HKDF/AES-GCM с нуля:
- настоящее TLS1.3-рукопожатие ЗАВЕРШАЕТСЯ УСПЕШНО при переиспользовании одного эфемерного секрета дважды (само по себе сильный сигнал — при любой путанице в патче рукопожатие просто не установилось бы);
- приложенческие данные реально проходят в обе стороны после рукопожатия (общий секрет действительно совпал, не только "TLS не упал");
- SessionId, перехваченный на проводе, открывается AES-256-GCM с AuthKey, выведенным СЕРВЕРНОЙ стороной независимо (ECDH(server_static, client_key_share_с_провода) + HKDF с солью из перехваченного `random`) — то есть клиент и независимый наблюдатель приходят к одному и тому же ключу;
- восстановленный plaintext несёт настроенный `short_id` и свежий timestamp.

**Собрано в `transport/`** (`core/src/transport/tcp_tls.rs`): `connect_tls_reality_with_alpn` строит `RealityHook` + `RealityCertVerifier::from_hook` из `VlessConfig::reality_params()`, конфигурирует `ClientConfig` через `builder_with_protocol_versions(&[TLS13]).dangerous().with_custom_certificate_verifier(...).with_no_client_auth()`, ставит `config.reality` и заданный ALPN; `connect_tls_reality` — то же без ALPN (голый TCP). Новая общая точка входа `connect_tls_by_security(cfg, alpn)` ветвится по `cfg.security` (`Reality` → REALITY-путь, `Tls`/`None` → обычная проверка цепочки X.509) и теперь используется ВСЕМИ тремя транспортами: `connect_and_handshake` (TCP), `transport::ws::connect_ws`, `transport::grpc::connect_grpc` — раньше только TCP-путь знал про `cfg.security`, WS и gRPC жёстко вызывали обычный `connect_tls`/`connect_tls_with_alpn`. Ссылка вида `vless://UUID@host:443?encryption=none&security=reality&sni=host&pbk=...&sid=...&type=ws|grpc|tcp` теперь рабочий путь для всех трёх транспортов.

Подтверждено, что REALITY-ветвление реально доходит до WS/gRPC (не теряется где-то в `type=`-диспетчеризации): `core/tests/reality_transports.rs` — сервер честно поднимает TLS через WS/h2, предъявляет Ed25519-самоподписанный сертификат с НАСТОЯЩЕЙ (не HMAC-патченной) подписью, и оба транспорта (`connect_and_handshake_ws`/`connect_and_handshake_grpc`) обязаны отвергнуть его именно через `RealityCertVerifier` (текст ошибки — HMAC-несовпадение, а не обычная "недоверенный корень" от резервного пути). Это не полный сквозной REALITY-хендшейк через WS/gRPC (см. следующий пункт, почему), но доказывает, что дальнейший код действительно исполняется, а не тихо остаётся на обычном TLS.

**Закрыто (сессия "доделать Этап 5 до конца"):** оба пункта выше ("не сделано") были закрыты честной, а не обходной дорогой — патчем и СЕРВЕРНОЙ части `vendor/rustls-reality-patch` тоже:

- `server/server_conn.rs`/`server/hs.rs`: у `ClientHello` (структура, которую rustls отдаёт `ResolvesServerCert::resolve`) появились два новых метода — `client_random()` и `client_key_share_x25519()`. Раньше резолвер сертификата вообще не видел ни `ClientHello.random`, ни key_share клиента (проверено по исходнику), поэтому написать тестовый сервер, который сам вычисляет AuthKey и подписывает сертификат HMAC'ом на лету, было невозможно без этого. Патч только ДОБАВЛЯЕТ два метода, читающих уже разобранные rustls'ом поля — ничего не пересчитывает заново и не меняет поведение существующих резолверов, которые эти методы просто не вызывают.
- `core/tests/reality_full_stack.rs` (новый файл) — тестовый REALITY-сервер (`RealityTestResolver: ResolvesServerCert`), который для каждого клиента вычисляет AuthKey (ECDH с его key_share + HKDF, код написан отдельно от `reality-core`, тот же принцип независимой перепроверки) и патчит DER сертификата HMAC-подписью на лету. Три теста — `reality_full_handshake_over_{tcp,ws,grpc}` — гоняют настоящий REALITY-хендшейк ЧЕРЕЗ БОЕВЫЕ функции (`connect_and_handshake`, `connect_and_handshake_ws`, `connect_and_handshake_grpc`), с настоящим `RealityCertVerifier` (не в обход, как в `reality_handshake.rs`), и с двусторонним обменом приложенческими данными. Все три проходят.
- Побочная находка по пути: тест `reality_full_handshake_over_grpc` сначала завис (не упал — именно завис навсегда). Причина была не в REALITY и не в gRPC-транспорте, а в самом тесте: сервер не досылал 2-байтный заголовок ответа VLESS (`[0x00, 0x00]`) перед payload — `vless_handshake` на клиенте читает эти 2 байта как заголовок, получал вместо этого первые 2 байта "pong", решал, что дальше нужно дочитать ещё ~111 байт несуществующих "аддонов", и вис на `read_exact` навсегда. Исправлено в тесте (досылка заголовка перед данными) — сама `connect_and_handshake_grpc` тут ни при чём, но полезно, что это вообще нашлось: до этой сессии НИ ОДИН тест не проверял `connect_and_handshake_grpc` целиком (`grpc_loopback.rs` намеренно вызывает её компоненты вручную, а саму функцию лишь упоминает, чтобы she линковалась) — то есть этот путь был непроверен runtime'ом с самого Этапа 4.

**Крипто-ревью — своя часть сделана:** в этой сессии добавлено укрепление памяти (`zeroize` — эфемерный X25519-секрет и общий ECDH-секрет в `reality/hook.rs` теперь стираются при `Drop`, не просто освобождаются как обычная память; feature `zeroize` у `x25519-dalek` делает то же для его собственных типов) — устраняет тихий, специфичный для крипто-кода риск, о котором предупреждает Этап 2. Но при **свежей** сверке (`curl` живого `main`-ветки `XTLS/reality` и `XTLS/Xray-core` прямо в этой сессии, не по памяти) нашлась находка, которая ниже описана и уже ЗАКРЫТА, а не осталась просто предупреждением:

⚠️→✅ **X25519MLKEM768 — было находкой, теперь реализовано.** С версии Xray-core 26.9.8+ REALITY-сервер требует гибридный постквантовый key_share `X25519MLKEM768` первым в списке, а не просто X25519 — прочитано построчно в `tls.go` (`XTLS/reality`, функция `Server`): `// reject outdated/strange Client Hello that doesn't have X25519MLKEM768 before optional X25519`. Независимо подтверждено открытыми баг-репортами sing-box ([#4520](https://github.com/SagerNet/sing-box/issues/4520)), karing ([#1952](https://github.com/KaringX/karing/issues/1952)), LxBox ([#142](https://github.com/Leadaxe/LxBox/issues/142)) — все с одинаковым симптомом против серверов на 26.9.8+.

**Реализация (следующая сессия "доделать X25519MLKEM768"):**
- `core/src/reality/hook.rs`: `RealityHook` теперь при создании генерирует ещё и пару ключей ML-KEM-768 (крейт `ml-kem` — pure-Rust реализация FIPS 203 от RustCrypto, того же семейства, что уже используемые в проекте `hkdf`/`hmac`/`x25519-dalek`; decapsulation key зеркалирует `x25519-dalek` и стирается при `Drop` через свою feature `zeroize`). `client_hybrid_key_share()` отдаёт 1216 байт (`ML-KEM768 encapsulation key(1184) || X25519(32)`); `complete_real_ecdh` при получении key_share сервера (1120 байт: `ML-KEM768 ciphertext(1088) || X25519(32)`) декапсулирует ML-KEM-часть и делает обычный X25519 ECDH, как и раньше, и склеивает секреты в порядке `mlkem || ecdh` (64 байта). Порядок байт и склейки сверен ДВАЖДЫ независимо: по `crypto/tls`/`crypto/mlkem` из стандартной библиотеки Go (там же, где теперь нативно живёт X25519MLKEM768) и по собственной реализации ЭТОЙ ЖЕ группы внутри самого используемого в проекте rustls (`vendor/rustls-reality-patch/src/crypto/aws_lc_rs/pq/{hybrid,mod}.rs`, `Layout { post_quantum_first: true, .. }`, `MLKEM768_ENCAP_LEN=1184`, `MLKEM768_CIPHERTEXT_LEN=1088`) — оба источника независимо совпадают байт-в-байт.
- `vendor/rustls-reality-patch/src/client/{client_conn,hs}.rs`: трейт `RealityClientHook::client_public_key()` (32 байта, только X25519) заменён на `client_hybrid_key_share()` (`Vec<u8>`, 1216 байт); `RealityKeyExchange::group()` жёстко возвращает `NamedGroup::X25519MLKEM768` (кодпоинт `0x11ec`, rustls уже знал его нативно — не пришлось трогать `msgs/enums.rs`); `named_groups` при активном REALITY сужен до этой же группы вместо голого X25519 (тот же приём, что уже был для X25519 — иначе повторяется HRR-несовпадение, пойманное раньше в этой же сессии для обычного X25519).
- `vendor/rustls-reality-patch/src/server/{server_conn,hs}.rs`: серверная функция `client_key_share_x25519()` (добавленная для тестового REALITY-сервера) теперь достаёт X25519 не только из голого `NamedGroup::X25519`, но и (в приоритете) из последних 32 байт гибридного key_share `X25519MLKEM768` — вынесено в общую `extract_client_x25519()`, используется в обоих местах, где раньше было дублирование.
- `core/src/fingerprint/client_hello.rs` (независимый от rustls разбор сырых байт с провода, Этап 3): тоже научился доставать X25519 из гибридной группы, с приоритетом над голым X25519 при наличии обеих — иначе `reality_handshake.rs` (независимая проверка AuthKey с нуля, без переиспользования `reality-core`) перестал бы видеть ключ клиента вообще. Три новых юнит-теста на это (`key_share_extracts_plain_x25519`, `key_share_extracts_x25519_tail_from_hybrid_mlkem768`, `key_share_prefers_hybrid_x25519_over_plain_x25519_when_both_present`).

**Подтверждено тестами, не только компиляцией:** после этих правок все три теста `reality_full_stack.rs` (TCP/WS/gRPC через настоящий `RealityCertVerifier`) и `reality_handshake.rs` (независимая AEAD-проверка с нуля) проходят БЕЗ ИЗМЕНЕНИЙ своей логики проверки — то есть новый гибридный key_share интероперирует с реализацией X25519MLKEM768 внутри самого используемого в проекте rustls (aws-lc-rs, `prefer-post-quantum` — фича по умолчанию в этом же патче) без единой правки тестового сервера под сам гибрид: серверная сторона всё поняла сама, потому что кодирует/декодирует ту же самую, стандартную группу. Интересная деталь по пути: изначально ошибочно предполагалось, что тестовому REALITY-серверу тоже придётся руками реализовывать гибрид — оказалось нет, `ServerConfig::builder()` с провайдером по умолчанию уже умеет X25519MLKEM768 "из коробки" (см. `DEFAULT_KX_GROUPS`/`ALL_KX_GROUPS` в `crypto/aws_lc_rs/mod.rs` патча) — это НЕ отменяет необходимость реализовывать гибрид вручную в `RealityHook` (REALITY требует полный контроль над каждым байтом key_share ради AuthKey/SessionId — см. докстринг `hook.rs`), но избавило от лишней работы на тестовой стороне.

⚠️→✅ **minClientVer/maxClientVer — было менее уверенной находкой, теперь закрыто.** Изначально держалось на одном неоднозначном баг-репорте (3x-ui [#5922](https://github.com/MHSanaei/3x-ui/issues/5922)) и характеризовалось как "менее вероятный, дешёвый в проверке пункт" без построчного подтверждения. Пользователь делегировал решение целиком ("выбирай, что надо, и приступай к работе"), с оговоркой не переусложнять и не копировать бездумно чужой код, экономить ресурсы, и в целом держать курс на практически полностью собственное ядро — так что перед реализацией код перепроверен заново, напрямую, построчно (`curl` живого `main` `XTLS/reality`, файл `tls.go`, не по памяти и не по пересказу баг-репорта):

```go
if (config.MinClientVer == nil || Value(hs.c.ClientVer[:]...) >= Value(config.MinClientVer...)) &&
    (config.MaxClientVer == nil || Value(hs.c.ClientVer[:]...) <= Value(config.MaxClientVer...)) &&
    (config.MaxTimeDiff == 0 || time.Since(hs.c.ClientTime).Abs() <= config.MaxTimeDiff) &&
    (config.ShortIds[hs.c.ClientShortId]) {
    hs.c.conn = conn
}
```

Значит: (1) проверка реальна и активна, не гипотетична — стоит в одном ряду с проверкой `ShortIds` и `MaxTimeDiff`; (2) она по-прежнему опциональна — `config.MinClientVer == nil`/`MaxClientVer == nil` (нулевое значение `[]byte` в Go, то есть поведение по умолчанию, если админ явно не задал `minClientVer=`/`maxClientVer=` в конфиге сервера) полностью её выключает — оценка "опционально по документации" подтвердилась, не опровергнута; (3) при провале сравнения сервер НЕ шлёт TLS alert — `hs.c.conn` просто не присваивается, и весь трафик прозрачно проксируется на сайт прикрытия, то есть для клиента это неотличимо от "сервер решил, что мы не REALITY-клиент" без какой-либо диагностики — тот же самый тихий отказ, а не громкая ошибка, что этот план призывает воспринимать серьёзно даже при низкой вероятности. `Value()` — просто упаковка байт в `int` big-endian (`core/core.go`: `Version_x/y/z byte`, сейчас `26.9.9` на `main`) — тот же порядок байт, что этот клиент уже использовал для reserved/timestamp/short_id.

Раз код реальный, а цена починки — три байта без какой-либо переработки протокола или архитектуры, реализовано: `core/src/reality/auth.rs` — константа `CLIENT_VERSION: [u8; 3] = [26, 9, 9]` (значение на момент этой правки соответствует актуальной ветке `main` Xray-core), `build_plaintext()` пишет её в байты `[0..3]` вместо нулей. Один источник истины (`hook.rs` вызывает ту же функцию) — правка в одном месте закрывает оба пути. Новый юнит-тест `build_plaintext_declares_nonzero_client_version` — регрессия именно против того, чтобы кто-то снова не обнулил эти байты по невнимательности. `cargo test --workspace` (49 тестов, было 48) и `cargo clippy --workspace --all-targets` — чисто.

Осознанный компромисс, не забытая работа: число `26.9.9` НЕ синхронизируется с апстримом Xray-core автоматически (никакого сетевого запроса на этапе сборки — это была бы прямая переинженерия ради второстепенной, по собственной оценке, находки) и неизбежно устареет по мере выхода новых версий сервера. Это не проблема протокола совместимости версий (клиент не притворяется, что понимает какие-то версия-специфичные фичи Xray-core — таких у REALITY-рукопожатия нет), а просто правдоподобное число вместо `0.0.0`, которое `minClientVer`, если задан, отверг бы почти наверняка. Если это всплывёт снова (например, сервер требует более свежую минимальную версию, чем `26.9.9`) — правка тривиальна, три байта в одной константе.

Сам факт, что протокол под ногами поменялся за то время, что шла эта работа (и что закрыть находку удалось в течение одной и той же сессии) иллюстрирует ровно то, о чём предупреждает Этап 3 про DPI-гонку, только применительно к REALITY: это не разовая сверка, а то, что нужно перепроверять регулярно.

**Статус крипто-ревью:** объём проверки расширен (укрепление памяти, полные сквозные тесты через настоящий `RealityCertVerifier` для всех трёх транспортов, свежая построчная сверка с живым исходником вместо кэшированного знания, теперь ещё и гибридный постквантовый key_share, сверенный с ДВУМЯ независимыми источниками истины) — но это ПО-ПРЕЖНЕМУ не заменяет стороннее ревью, которое план требует "до начала, не после". Патч rustls (клиент + сервер для тестов) продолжает расти в размере и сложности, и каждое такое расширение — не повод меньше настаивать на независимом ревью, а повод настаивать на нём больше: чем больше поверхность, тем дороже одна пропущенная ошибка.

## Этап 6 — Zero-copy оптимизация
- Splice применим только на серверной стороне (сервер↔назначение), не в клиентском SOCKS5-сценарии.
- (Существенных дополнительных рисков здесь нет — эта часть больше инженерная, чем стратегическая.)

**Статус: не применимо к этому ядру, не доработка "на потом" — архитектурный факт.**
Этот репозиторий реализует только клиента (SOCKS5 → VLESS), сервера здесь
никогда не было и не планировалось (см. описание проекта). `splice(2)`
даёт нулевое копирование, только когда данные идут между двумя
файловыми дескрипторами БЕЗ прохода через userspace — то есть когда
хотя бы одна из сторон релея не требует расшифровки/шифрования в
процессе. У сервера VLESS это в принципе возможно на плече
"сервер↔конечное назначение" (если конечное назначение — открытый
plaintext-сокет). У клиента же **обе стороны каждого релея всегда
проходят через TLS в userspace** (`rustls` не использует kernel TLS
offload/`ktls`): один конец — локальный SOCKS5-сокет от приложения
пользователя (данные уже расшифрованы приложением или предназначены
для шифрования нами), другой — VLESS-сервер поверх TLS/WS/gRPC. Байты
физически обязаны попасть в userspace хотя бы раз на каждое
направление, чтобы rustls их зашифровал/расшифровал — `splice`
здесь неприменим сам по себе, а не "ещё не реализован". Буфер-на-соединение
из Этапа 2 (`relay.rs`) — это и есть релевантная для клиента оптимизация
копирования; дальше в эту сторону имеет смысл двигаться, только если
Этап 6 переносится на серверную часть, которой в этом проекте нет.

## Этап 7 — Профилирование
- Тестировать альтернативные аллокаторы на обоих сценариях (простой/нагрузка), выбор через feature-flag сборки.
- ⚠️ **Ограниченность тестового стенда:** профилирование на своей машине не отражает поведение на реальном VPS с другим ядром ОС/памятью — финальную профилировку стоит повторить на типичном сервере из тех, где реально будет разворачиваться ядро.

**Статус: ✅ готово** (в границах, которые честно накладывает песочница — см. предупреждение выше, оно применимо буквально: сборка идёт в облачном контейнере, не на типичном VPS).

**Реализовано:** `bin/client` и `bench` получили feature-flag `mimalloc`
(опциональная зависимость `mimalloc = "0.1"`, `#[global_allocator]` под
`#[cfg(feature = "mimalloc")]` — дефолтная сборка не меняется, системный
аллокатор (glibc malloc на Linux) остаётся дефолтом). Сравнение прогнано
дважды прямо в этой песочнице — с реальными числами, не абстрактно:

- **Простой (idle) сценарий:** `reality-client` запущен с валидной
  ссылкой и слушающим SOCKS5, но без единого реального соединения;
  RSS/PSS снят `bench/src/bin/memwatch.rs` снаружи процесса за 5 секунд.
  Системный аллокатор: **~4.5 МБ RSS / ~2.9 МБ PSS**, стабильно.
  mimalloc: **~11.2 МБ RSS / ~9.5 МБ PSS**, тоже стабильно, но в ~2.5
  раза выше — mimalloc заранее резервирует более крупные сегменты
  памяти (это его обычный компромисс "throughput/фрагментация под
  нагрузкой" в обмен на бóльший базовый footprint), и для клиента,
  который бóльшую часть времени просто ждёт сетевого ввода-вывода
  (idle — типичный режим, не крайний случай), это прямой минус.
- **Нагрузка:** `cargo bench -p bench --bench throughput` (кодирование
  VLESS-заголовка — короткоживущий `Vec<u8>` на каждый вызов; релей на
  4/64/1024 КБ in-memory duplex-потоках) прогнан в режиме `--quick`
  дважды — с дефолтным аллокатором и с `--features mimalloc`. Кодирование
  заголовка показало направленное ускорение (~31 → ~18.5 нс на вызов,
  вроде бы почти вдвое), но при `--quick`-выборке сам criterion пометил
  это как "no change in performance detected" (p ≈ 0.06 > 0.05) — то
  есть сигнал есть, но недостаточно измерений в песочнице, чтобы
  утверждать его уверенно; на релее показатели по всем трём размерам
  колебались в обе стороны без статистической значимости вообще. Не
  переигрывать длинными прогонами специально ради этого замера в
  контейнере, где "типичного VPS" всё равно нет (см. предупреждение
  плана) — цифры здесь для порядка величины, а не для окончательного
  решения.

**Вывод:** для ИМЕННО этого клиента (доминирует ожидание сетевого I/O,
а не аллокационно-тяжёлый hot path) системный аллокатор по умолчанию —
разумный дефолт: 2.5x разница в idle RSS реальна и воспроизводима,
а ускорение на нагрузке в этой песочнице не подтверждено статистически.
`--features mimalloc` оставлен как опция для тех, кто профилирует
собственное развёртывание и находит у себя действительно
аллокационно-узкое место — решение оставлено за пользователем, не
зашито в билд по умолчанию.

   учётных данных или прав публиковать что-либо от имени пользователя,
   и решение "публиковать ли вообще" — с учётом юридического риска,
   который сам план требует оценить, и того, что крипто-ревью Этапа 5
   так и не было — тем более не то, что стоит решать за пользователя
   молча.

**Что нужно сделать пользователю самостоятельно** (аналогично `cargo
miri` в Этапе 2 — честно вынесено сюда, а не тихо пропущено):
- поставить Xray-core локально (или на том же VPS, где в итоге будет
  разворачиваться это ядро) и прогнать `bench/benches/throughput.rs`-эквивалентный
  сценарий (или просто одинаковый realistic-трафик) против обоих
  через `bench/src/bin/memwatch.rs` — оно уже умеет мерить RSS/PSS
  произвольного PID, включая чужой (Xray-core) процесс, без
  инструментирования;
- прогнать сравнение на типичном VPS, не на разработческой машине (то
  же предупреждение, что в Этапе 7);
- закрыть открытый пункт крипто-ревью Этапа 5 до всякой публикации —
  и только после этого решать вопрос "публиковать или нет" с учётом
  собственной юридической оценки, уже сделанной ранее.

## Общая пометка над всем планом

⚠️ **Главный стратегический риск — соотношение время/выигрыш.** Весь план реалистично — это многие месяцы работы одного разработчика, включая постоянное сопровождение (Этап 3, гонка с DPI). Прежде чем начинать Этап 1, стоит явно ответить себе: превышает ли ожидаемый выигрыш (условные "0.5-2 МБ RSS/соединение экономии") стоимость этого времени и риска — юридического и крипто-ошибок — по сравнению с тем, чтобы просто использовать/патчить готовое ядро под свои задачи.
