### Детальный проход по контракту C ABI

На ветке аудита после PR #92 поочерёдно сопоставлены 16 экспортов из `ffi/abi-baseline.json`, объявлений `ffi/include/reality.h`, тел `rc_*` в `ffi/src/lib.rs` и строк quick reference в `docs/LIBRARY.md` / `docs/LIBRARY.en.md`. Подтверждено по текущей реализации: выделенные библиотекой строки освобождаются через `rc_free_string`, кроме статической строки `rc_version`; Unix TUN FD передаётся ядру при вызове `rc_start`, тогда как на не-Unix допустим только `-1`; process-wide callbacks `rc_set_protect` и `rc_set_connection_owner` допускают замену/снятие и ждут активные вызовы; event/log callbacks передают временную JSON-строку и не должны повторно вызывать API того же handle; `rc_stop(NULL)` и `rc_free_string(NULL)` являются no-op; базовые числовые категории ошибок совпадают с enum из заголовка. RU и EN quick-reference таблицы перечисляют одинаковые функции и соответствующие ограничения.

В NULL/result/ownership полях таблицы расхождений с кодом или между языковыми версиями не найдено. Смысловое преувеличение охвата `rc_request` за пределы обычных локальных маршрутов зафиксировано отдельно в A-12. Этот проход не подтверждает исчерпывающее покрытие всех HTTP-маршрутов локального API, успешность callback-сценариев на каждой платформе, безопасность произвольных указателей или полный runtime-контракт host-приложения; эти темы остаются в соответствующих тематических аудитах. Изменений кода/ABI не вносилось.

Пути и строки выше — anchor points для аудита, они могут сместиться при редактировании. Перед публикацией каждого тематического PR доказательства нужно получить заново на его base SHA.

## Дальнейший аудит и PR gates

1. PR-01: завершить проверку актуальных фактов, внутренних/внешних ссылок и повторов по всем собственным строкам матрицы; приложить подтверждения из кода, тестов, CI и релизов. Отдельно перечислить исключения `vendor/`.
2. PR-02: предложить `docs/STYLE_GUIDE.md`, `docs/STYLE_GUIDE.en.md`, `docs/GLOSSARY.md`, `docs/GLOSSARY.en.md` и навигацию. До пользовательского согласования этих правил PR-03…PR-08 не начинать массовую редактуру.
3. PR-03…PR-08: проходить небольшими тематическими изменениями, только после принятия стандарта; для каждого PR заново фиксировать base SHA, затронутые файлы, кодовые доказательства, RU/EN и проверки.
4. Для каждого PR выполнить `git diff --check`, `python scripts/check_doc_links.py`, соответствующую проверку примеров/ABI и CI. Ни один PR не объединять без отдельного разрешения пользователя; разрешение на merge не отменяет требования зелёных обязательных checks.
5. После каждого merge повторить проверку на актуальном `main`. В конце провести независимый аудит с чистого checkout и подготовить отчёт по шаблону VCTWS.

## Ограничения исходного аудита

- Одноразовая проверка 2026-11-05 проверила 72 уникальные HTTP(S)-ссылки в Markdown области аудита: все вернули HTTP 2xx или 3xx (HEAD; для 403/405/501 использовался GET с `Range: bytes=0-0`). Это подтверждает только доступность на момент проверки, а не правильность назначения, свежесть содержания или отсутствие нежелательного redirect; A-51 показывает эту границу.
- Подсчёт пар и таблиц — структурная проверка, а не семантическое доказательство качества перевода.
- Строки с назначением этапов являются планом проверки. Они не утверждают, что все технические факты уже верифицированы.
- Любую найденную ошибку кода фиксировать отдельной задачей; данный план не разрешает менять поведение ядра, ABI/API, формат конфигурации или протоколы.
