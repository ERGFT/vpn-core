# Проверка, сравнение и производительность

**Русский** | [English](TESTING.en.md)

Как проверяется проект, сравнение с Xray-core, замеры памяти и скорости.

## Проверка проекта

Одной командой — всё, что доступно на этой машине:

```sh
scripts/ci.sh          # все доступные проверки; внешние инструменты запускаются, если установлены
scripts/ci.sh --quick  # fmt, SPDX, ссылки, синтаксис скриптов, clippy без предупреждений, тесты
```

`--quick` пропускает release-сборку, интеропы и сквозные проверки,
платформенные сборки и проверки патчей зависимостей. Без этого флага скрипт
запускает все доступные ему дополнительные проверки; недоступные инструменты
обозначаются как `SKIP`.

Отдельно:

Unit-тесты `core/src/transport/tcp_tls.rs` используют виртуальные часы для
проверки чередования IPv4/IPv6, быстрого перехода ко второму семейству,
повторной попытки после отказа, ограничения числа адресов и двух одновременных
попыток, а также общего срока подключения — без зависимости от внешней сети и
DNS.

`cargo test -p reality-core protocol_architecture_test` запускает внутренний
тестовый proxy: типизированные настройки и фабрику, TCP и UDP echo через
`Outbound`/router, проверку настроек, отказ при недоступном сервере, таймаут,
сигнал отмены tracker и замену router при сохранении уже открытого TCP-потока.
Этот fixture подключён через `#[cfg(test)]`; он не является пользовательским
протоколом и не попадает в release-сборки.

На GitHub workflow `.github/workflows/ci.yml` запускается при push в `main`
и для каждого pull request. Job `linux` выполняет `scripts/ci.sh`, проверку
C ABI, список лицензий и TUN в netns; последний шаг пропускается для PR из
форков. Job `windows` на **настоящей Windows** выполняет тесты, сборку
`.exe` (его можно скачать со страницы запуска, «Artifacts») и
`scripts/windows_live_test.ps1`: служба, права её папки и TUN с настоящим
трафиком.

Кроме них запускаются отдельные jobs: `audit` проверяет advisories и
источники зависимостей, включая отдельно патченный rustls; `msrv` собирает
workspace на Rust 1.89; `coverage` публикует lcov-отчёт без порога покрытия;
`secrets` ищет секреты во всей истории Git. Еженедельный запуск по расписанию
выполняет только `audit`. Job `mobile` описан ниже. Руководство по проверке
и выпуску находится в [RELEASING.md](RELEASING.md). Для нового выпуска используйте
только ранее не опубликованную версию и тег; `v0.1.0` уже существует. Сначала
запустите непубликующий preflight на точном SHA `main`, затем отправьте новый
тег на проверенный SHA. Preflight не создаёт релиз; workflow тега публикует
релиз (не черновик) только после успешной сборки CLI и всех SDK. Проверка
attestation: `gh attestation verify <файл> --repo ERGFT/vpn-core`.

Отдельная задача `mobile` кросс-компилирует `reality-ffi` для Android
arm64-v8a и iOS arm64. Ошибка этой задачи не делает workflow неуспешным
(`continue-on-error: true`); успешная сборка подтверждает компиляцию
библиотеки, но не её запуск на устройстве.

Релизный workflow прикладывает к CLI SDK C ABI для Linux x86_64, Windows
x86_64, macOS arm64, Android arm64-v8a и iOS arm64. Состав и metadata архива
зависят от версии; не переносите возможности текущего packaging на старые ZIP.

Xray-core для тестов: `scripts/fetch_xray.sh` (скачать релиз) или
`scripts/build_xray_from_source.sh` (собрать из исходников по git — для
сред без доступа к релизам и `proxy.golang.org`). В такой же среде
Go-стенд готовит `scripts/interop_sandbox_bootstrap.sh`.

## Сравнение с Xray-core

`scripts/stage8_compare_with_xray.sh` — автоматическое сравнение с
настоящим Xray-core на одинаковой нагрузке (оба клиента ходят на один
тестовый REALITY-сервер, нагрузку даёт один и тот же код). Три прогона,
8 соединений x 16 МиБ, loopback, 2 ядра, Xray-core 26.9.9:

| показатель | reality-core | Xray-core 26.9.9 |
|---|---|---|
| память на холостом ходу | **6,3 МиБ** | 30,4 МиБ |
| пик памяти под нагрузкой | **8,9 МиБ** | 35,3 МиБ |
| до первого байта данных | 25,4 мс | 35,8 мс |
| пропускная способность | 625 МиБ/с | 572 МиБ/с |

Это историческая сводка, записанная в [журнале проекта](../PLAN.md) для
перемера от 2026-09-26. В репозитории нет исходных JSON/CSV трёх прогонов,
модели машины и разброса между результатами. Поэтому таблица не позволяет
определить способ агрегирования трёх прогонов или сделать вывод о значимом
различии результатов; прежняя пометка «ничья» не подтверждена доступными
исходными данными. Один запуск текущего скрипта выполняет один замер для
каждого клиента и сохраняет JSON/CSV в `target/stage8/`; он не повторяет
измерение три раза. Для нового сравнения сохраняйте данные каждого запуска,
окружение и SHA скрипта отдельно.

Xray-core охватывает больше протоколов и сценариев маршрутизации. `vpn-core`
тоже включает DNS, TUN, правила, группы серверов, подписки, локальное API и
C ABI, но его протокольный охват и экосистема уже. Эта таблица сравнивает
только конкретный сценарий ниже; она не является сравнением полноты функций.

⚠️ Время до **первого байта данных**, а не до ответа на SOCKS5 CONNECT:
Xray отвечает на CONNECT авансом, не дожидаясь соединения с сервером
(отвечает «успех», даже если сервера нет), поэтому его ответ на CONNECT
с нашим сравнивать нельзя. Подробности — `PLAN.md`, Этап 8.

## Сравнение с xray-rust

Для нового сравнения используйте отдельный сценарий, не старую таблицу выше:

```sh
scripts/fetch_xray.sh
scripts/stage6_compare_with_xray_rust.sh
```

Сценарий закрепляет `xray-rust` на теге `v0.8.0` (коммит
[`fcce4be`](https://github.com/aimalygin/xray-rust/tree/fcce4be2771c1fb3f11e9503741d39a4d8df314e))
и использует Xray-core `v26.9.9` как общий сервер VLESS + REALITY + Vision.
Оба клиента запускаются на одной машине с одинаковыми параметрами, Chrome
fingerprint, восемью одновременными потоками и внутренним TLS 1.3 echo.
Каждый поток поочерёдно отправляет блок 64 КиБ и проверяет его эхо до отправки
следующего; восемь потоков работают параллельно. Порядок клиентов чередуется
между пятью прогонами. По каждому прогону
сохраняются JSON и CSV RSS/PSS; итоговый manifest фиксирует коммиты,
версии бинарников, SHA-256, ОС и модель CPU. Метрики: пропускная способность,
время до первых прикладных данных после TLS handshake, idle/peak RSS/PSS,
миллисекунды CPU на переданный GiB и восстановление прикладного запроса.

Настройки можно менять через `RUNS`, `CONNS`, `MIB`, `OUTDIR`. Результаты
появляются в `target/stage6-xray-rust/`; по умолчанию каждый из пяти прогонов
передаёт 8 × 64 МиБ в каждую сторону для каждого ядра. Затем общий сервер
останавливается на `OUTAGE_SECS` (по умолчанию 2 секунды) и запускается снова;
процесс клиента остаётся запущенным. `stage6_recovery_probe.py` повторяет SOCKS5
CONNECT и внутренний TLS 1.3 echo до первого успешного запроса. Результат от
TCP-готовности сервера до успешного echo записывается отдельно в
`*.recovery.json`; `RECOVERY_POLL_MS` задаёт интервал опроса, а
`RECOVERY_TIMEOUT_SECS` — предел ожидания. Сохраняйте параметры вместе с
сырыми JSON/CSV и не сводите вывод к одной лучшей попытке. Это loopback-сценарий
отказа и восстановления сервера, а не физического сетевого интерфейса: он не
моделирует WAN-потери, энергопотребление или обработку host-сигнала
`rc_network_changed`. Выводы появятся только после успешного полного прогона.

### Результаты первого опубликованного прогона

Запуск [GitHub Actions #41678957797](https://github.com/ERGFT/vpn-core/actions/runs/41678957797)
успешно завершил все пять парных прогонов на `ubuntu-24.04` (Azure, x86_64,
AMD EPYC 9V74, 4 логических CPU). Ниже — медианы; полный manifest и все
покомпонентные JSON/CSV доступны в артефакте запуска в течение 30 дней.

| Метрика | vpn-core | xray-rust v0.8.0 | Наблюдение в этом сценарии |
|---|---:|---:|---|
| Пропускная способность, МиБ/с | 24,280 | 23,967 | vpn-core выше примерно на 1,3% |
| Первый байт после TLS handshake, мс | 40,994 | 41,140 | vpn-core быстрее примерно на 0,4% |
| Пиковый PSS, КиБ | 11 405 | 14 641 | vpn-core ниже примерно на 22,1% |
| CPU, мс на переданный ГиБ | 980 | 1 260 | vpn-core потребил примерно на 22,2% меньше CPU |
| Восстановление после перезапуска сервера, мс | 86,230 | 45,939 | xray-rust восстановился быстрее |

Это один облачный runner, loopback, один профиль и пять повторов; версии Rust
сборки различались (`1.99.1` для vpn-core и `1.96.0` для xray-rust). Это
воспроизводимая отправная точка, а не независимый VPS-бенчмарк и не обещание
преимущества в реальной сети. В частности, восстановление включает опрос с
интервалом 50 мс, поэтому разницу нельзя интерпретировать как универсальную
скорость восстановления после смены сети.

## Производительность и память

Бенчмарки и выбор аллокатора — `PLAN.md`, Этапы 0 и 7. Кратко: один буфер
(17 КиБ — чтобы вмещался целый TLS-рекорд, это важно для Vision) на
направление соединения, без глобального пула; системный аллокатор по
умолчанию (`--features mimalloc` — опционально, в замерах давал больший
idle RSS).

```sh
cargo bench -p bench
cargo run -p bench --bin memwatch -- --pid <PID> --duration-secs 30 --csv rss.csv   # Linux
```
