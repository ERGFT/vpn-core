# Приложения и сайты в одном TUN

Статус: **экспериментально**, API ядра и C ABI. Интеграция конкретного Android
клиента и проверка на устройстве этим изменением не выполняются.

Правила `route.rules` поддерживают `user_id` (UID ОС: число или массив чисел)
и `invert` (инверсия всего предиката). Срабатывает первое правило; внутри UID
списка — «или», с доменом/портом/сетью/входом — «и». Например:

```json
{
  "route": {
    "rules": [
      {"domain_suffix": ["bypass.example"], "outbound": "direct"},
      {"user_id": [10001], "outbound": "proxy"},
      {"user_id": [10001], "invert": true, "outbound": "direct"}
    ],
    "final": "proxy"
  }
}
```

UID 10001 идёт через proxy, остальные известные UID — напрямую, сайт и его
поддомены — напрямую независимо от приложения. Имена выходов должны существовать.
Порядок правил задаёт клиент, а не ядро: правило приложения, поставленное раньше
сайта, будет иметь приоритет. Fake-IP восстанавливается до маршрутизации.

## Доверенные метаданные

Перед запуском приложение устанавливает `rc_set_connection_owner(callback, user)`
или Rust `connection_owner::set_callback`. Callback получает IP protocol 6/17 и
исходные числовые адреса `SocketAddr` до fake-IP/sniffing; IPv6 записан в скобках.
Ответ — UID 0..UINT32_MAX либо -1/None, если владелец неизвестен. В C строки
действительны только во время callback. Отрицательные и слишком большие UID не принимаются.

Callback вызывается один раз на новый TCP/UDP-поток TUN, только если маршрутизатор
содержит UID-правила. Он не вызывается на каждый пакет, не кешируется бессрочно
по порту и не используется для SOCKS/HTTP или внутренних DNS/health соединений.
Это глобальная настройка процесса: установить до старта, снять после остановки
всех ядер и завершения callback; `user` должен оставаться живым и потокобезопасным.
Вызов синхронный: не блокировать его, не выполнять сетевые запросы, не выбрасывать
исключения через C ABI. Старый C ABI не изменён, добавлен отдельный символ.
У Rust `Metadata` появилось поле `user_id: Option<u32>`.

Если нужное по порядку UID-правило не может узнать владельца, поток блокируется
выходом `connection-owner-unavailable`, а не уходит через final/direct. Даже
инверсия не превращает неизвестное приложение в «невыбранное». Предыдущие
самодостаточные правила сайта/входа работают без UID. Правила режима global/direct
по-прежнему обходятся явно выбранным режимом; гарантия относится к режиму rule.
DNS hijack обслуживается до маршрутизации приложений, как и раньше.

## Что нужно сделать в Android-клиенте

1. В JNI подключить новый callback к `ConnectivityManager.getConnectionOwnerUid`
   (Android API 29+), используя исходную пару адресов TCP/UDP. Ошибка/неизвестный
   UID возвращает -1, а не UID самого VPN.
2. `package_name` преобразовать в UID через `ApplicationInfo.uid`. Ядро не читает
   список Android-пакетов и не принимает package_name как доказательство владельца.
   Приложения с shared UID нельзя разделить этим механизмом; сообщить это пользователю.
3. Для смешанных правил пропустить все нужные приложения через TUN: прежний
   `addAllowedApplication`/`addDisallowedApplication` не должен обходить правила сайтов.
   Собственные защищённые сокеты VPN по-прежнему исключаются через protect.
4. Правила сайтов разместить перед UID-правилами в соответствии с политикой клиента.
   Не выбрасывать дополнительные правила и не снимать старый запрет до подключения
   resolver, адаптера и проверки DNS/fake-IP/TCP/UDP на устройстве.
5. На API 24–28 без надёжного resolver совместный режим не включать. Не подставлять
   выдуманный UID и не заменять неизвестный UID прямым выходом.

Это не автоматический ремонт существующего APK NOVA: ему нужны новая нативная
библиотека и отдельные изменения JNI/адаптера. Реальные приложения, shared UID,
смена сетей, DNS приложений/DoH и расход батареи требуют испытаний на устройстве.
