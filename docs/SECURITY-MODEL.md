# Модель безопасности

**Русский** | [English](SECURITY-MODEL.en.md)

Какие свойства безопасности предоставляет клиент, при каких условиях они действуют и какие угрозы остаются. Как сообщить об уязвимости — [SECURITY.md](../SECURITY.md).

## Безопасность

История и область внутренней проверки описаны в [PLAN.md](../PLAN.md), раздел «Аудит безопасности (2026-09-26)».

- **Кому уходит UUID — зависит от `security`:**
  - `reality` — только серверу, прошедшему проверку REALITY. Данные VLESS
    отправляются после полного рукопожатия с проверкой (HMAC сертификата,
    ML-DSA-65 при `pqv=`). Если проверка REALITY не прошла, клиент
    проверяет сертификат как обычный браузер только для того, чтобы
    правдоподобно завершить рукопожатие (см. ниже): такое соединение
    приложению не отдаётся и UUID по нему не уходит. Вырожденный `pbk=`
    отвергается.
  - `tls` — тому, кто предъявил действительный сертификат для имени из
    `sni=` (по встроенному набору корней или `--ca`): защита — та же, что
    у HTTPS, UUID получит любой, у кого есть действительный сертификат для
    этого имени.
  - `none` — открытым текстом: UUID и трафик видят все на пути до сервера.
    CLI требует для неё `--allow-insecure`; в sing-box-конфигурации
    задайте расширение ядра `allow_insecure: true` для выхода VLESS/Trojan
    ([руководство](CONFIG.md)). C ABI получает конфигурацию от host-приложения,
    а не CLI-аргументы ([SDK](LIBRARY.md)).
- **Если вместо REALITY-сервера отвечает настоящий сайт:** после проверки
  сертификата как обычного TLS клиент запускает в фоне один запрос `GET /`
  с заголовками выбранного профиля браузера. Ошибку REALITY клиент возвращает
  сразу, не ожидая ответа этого запроса; сам фоновый запрос может завершиться
  ошибкой или по таймауту. Заголовок VLESS и UUID по такому соединению не
  отправляются. Это упрощённая имитация: выполняется один запрос, а не
  открывается полноценный браузер. Без параметра `fp=` используется профиль
  Chrome; поддерживаемые значения `fp=` выбирают другие профили.
- **DNS для проксируемого трафика:** если приложение передаёт имя сайта
  (SOCKS5 с именем, HTTP-прокси, TUN с fake-IP), имя разрешает сервер, и
  локальный DNS его не видит. Локальной сети могут быть видны:
  - имя самого VLESS-сервера;
  - имена, которые приложение разрешило само до подключения (например,
    браузер с SOCKS5 без «DNS через SOCKS v5»);
  - имена для выхода `direct`: при настроенном разделе `dns` их разрешает
    выбранный DNS-сервер, иначе — системный резолвер. Сервер без явного
    `detour` использует `route.final`, а если он не задан — первый outbound
    (обычно VLESS). При `detour: direct`
    локальная сеть видит адрес DNS-сервера; содержимое запроса видно только
    для незашифрованных UDP/TCP DNS. DoT, DoH и DoQ шифруют DNS-запрос.
    `type: local` передаёт разрешение системному резолверу, а его видимость
    зависит от настроек ОС;
  - имена, которые `domain_strategy: ip_if_non_match` разрешает для
    правил по IP, — через выбранный DNS-сервер и его `detour`. При прямом
    незашифрованном DNS-запросе имя видно локальной сети.
- **Локальный прокси не держится за «мёртвые» соединения:** 10 с на
  приветствие SOCKS5/HTTP, закрытие по простою (300 с; 30 с, если одна сторона
  уже закрылась), до 512 одновременных соединений на каждый вход по умолчанию;
  лимит настраивается через `max_conns`.
- **Некоторые разборщики ограничивают размер входных данных, но это не
  гарантия защиты от сбоев или DoS.** gRPC-декодер отклоняет сообщение с
  объявленным размером больше 4 МиБ после чтения 5-байтового заголовка,
  не дожидаясь накопления всего сообщения; это покрыто тестом
  `rejects_oversized_message_before_buffering_it`. WebSocket настраивает
  пределы кадра и сообщения в 1 МиБ в используемом парсере. Для XHTTP
  HTTP/2-клиент задаёт предел списка заголовков 256 КиБ; это не ограничение
  размера тела. Эти значения описывают конкретные настройки, а не доказывают
  безопасность всех путей HTTP или отсутствие ошибок при обработке входных
  данных.
- **UDP-ассоциацией пользуется только её владелец** (IP и порт), а не
  любой процесс на той же машине.

## Если злоумышленник в той же Wi-Fi сети

Что он **не** может (при `security=reality` или `tls`):

- прочитать или подменить трафик до сервера и узнать UUID — даже если
  перехватит соединение (подмена DNS, поддельная точка доступа): без
  ключа сервера он не пройдёт проверку REALITY, без доверенного
  сертификата — проверку TLS; рукопожатие обрывается до отправки UUID;
- подключиться к прокси: по умолчанию он слушает только `127.0.0.1`.

Что он **может**, и как это закрыто:

| Что | Защита |
|---|---|
| Ссылка с `security=none`: UUID и трафик видны всем в сети, сервером может пользоваться кто угодно | CLI не запускает такую ссылку без `--allow-insecure`; для sing-box/SDK-конфигурации см. [`allow_insecure`](CONFIG.md) и [контракт SDK](LIBRARY.md) |
| Прокси открыт в сеть (`--listen 0.0.0.0`): подбор пароля | пароль не короче 12 байт в UTF-8; после 5 неверных попыток адрес блокируется на 60 секунд, следующие блокировки удваиваются до 1 часа. Учёт IPv6 ведётся по подсети `/64`; успешная авторизация сбрасывает историю ошибок. Список `--allow-ip` дополнительно ограничивает клиентов |
| Управляющий API доступен из сети: владелец токена может менять настройки и управлять клиентом; `GET /config` раскрывает UUID и пароли | оставляйте API на loopback. Для сетевого доступа нужен токен не короче 16 байт и `allow_ip`; проверяются `Host` и браузерный `Origin`. `allow_query_token` принимает `?token=` только для WebSocket; включайте его лишь если это нужно клиенту: URL с токеном может попасть в журналы и историю браузера. Файлы панели и `GET /` доступны без токена, но не дают доступа к защищённым API-маршрутам |
| Прокси открыт в сеть: SOCKS5 и HTTP-прокси **не шифруют соединение до прокси** — в общей Wi-Fi видны пароль и адреса сайтов; содержимое незашифрованного трафика тоже видно. HTTPS защищает содержимое своим TLS | так устроены сами эти протоколы, клиент это исправить не может; клиент предупреждает при запуске. Открывайте прокси в сеть только дома, для своих устройств, с `--allow-ip` |
| Прокси открыт в сеть, и есть правило с выходом `direct`: устройство из сети ходит «от имени» этого компьютера — в том числе в сети, куда оно само не достаёт (рабочий VPN, Docker, WSL) | для клиентов не с loopback `direct` блокирует loopback- и unspecified-адреса, а также link-local IPv4/IPv6 (включая `169.254.169.254`); локальному клиенту доступ к своему компьютеру разрешён. Это ограничение не является универсальной защитой от SSRF. Остальное — пускайте в прокси только свои устройства (пароль, `--allow-ip`) и не направляйте в `direct` подсети, которые им не нужны |
| Видит IP сервера, имя `sni=` в ClientHello, объём и время трафика | VPN не скрывает эти метаданные. REALITY использует ClientHello с выбранным браузерным профилем и `sni=`, но не скрывает IP и весь рисунок трафика и не превращает соединение в полноценную сессию браузера |
| DNS-запросы в локальной сети видны и подменяемы (обычный DNS не шифруется) | раздел `dns` с DoH/DoT через сервер и DNS-вход (`direct` + правило `hijack-dns`) как системный DNS; ответы UDP проверяются (номер, вопрос, адрес сервера) |
| Трафик программ, которым **не** указан прокси, идёт мимо него | это прокси, а не системный VPN: настраивайте программы или включите `--system-proxy` (Windows; его слушаются не все программы); в браузере с SOCKS5 включите «DNS через SOCKS v5», иначе имена сайтов уходят в DNS локальной сети (с HTTP-прокси имена и так уходят прокси) |
