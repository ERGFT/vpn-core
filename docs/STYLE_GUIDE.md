# Стандарт технической документации VCTWS 1.0

[Русский](STYLE_GUIDE.md) | [English](STYLE_GUIDE.en.md) · [Глоссарий](GLOSSARY.md)

Этот стандарт задаёт редакционные правила проекта для документации на русском и английском языках. Он адаптирует отдельные практики [ASD-STE100](https://www.asd-ste100.org/about.html), [Google Developer Documentation Style Guide](https://developers.google.com/style) и [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide). **Это внутренний стандарт проекта, а не заявление о формальном соответствии этим руководствам.**

Порядок приоритетов: техническая достоверность → безопасность и ограничения → однозначность → полнота контрактов → навигация → единообразие → краткость.

## Обязательность правил

- **MUST** — правило обязательно. Исключение требуется обосновать, если оно затрагивает техническую точность, безопасность, ограничения или публичный контракт.
- **SHOULD** — следуйте правилу, если это не мешает точности и ясности.
- **MAY** — допустимый вариант.

Эти слова описывают редакционные требования VCTWS. В спецификациях протоколов и API нормативные слова имеют смысл, заданный самой спецификацией; не переносите на них определения VCTWS. Если документ использует термины RFC 2119/8174, явно укажите это.

## Типы документов и их задача

| Класс | Примеры | Читатель должен найти |
|---|---|---|
| Презентационный | `README.md` | Что такое проект, кому он подходит, как начать, каковы ограничения и куда читать дальше |
| Процедурный | `CLI.md`, `TUN.md`, `WINDOWS.md`, `RELEASING.md` | Условия, действия, наблюдаемый результат и диагностику |
| Технический справочник | `CONFIG.md`, `DNS.md`, `LINK.md`, `API.md`, `LIBRARY.md` | Точные значения, контракты, ошибки и ограничения |
| Инженерное описание | `ARCHITECTURE.md`, `REPOSITORY.md`, `RUSTLS_PATCH.md`, `APPLICATION_ROUTING.md` | Компоненты, потоки данных, инварианты, причины решений и пределы |
| Безопасность и тестирование | `SECURITY-MODEL.md`, `TESTING.md`, review-документы | Условия, доказательства, допущения и пределы проверок |
| Исторический | `PLAN.md`, `CHANGELOG.md`, отчёты | Дату, объект проверки и состояние именно на тот момент |
| Правила проекта | `CONTRIBUTING.md`, `SECURITY.md`, шаблоны GitHub | Точные правила и воспроизводимые действия |

Для нового или изменённого документа указывайте читателю один основной источник по теме. Не дублируйте подробный справочник в README или соседнем руководстве; оставьте краткий обзор и ссылку. Перед сокращением убедитесь, что уникальные ограничения и примеры сохранены.

### Исключение для README

README может использовать более выразительную подачу, таблицы сравнения и визуальные элементы. Он **MUST** сохранять подтверждённость технических утверждений, явно показывать важные ограничения и отличать ядро/SDK от готового приложения. Не обещайте возможности или безопасность без доказательств.

## Ясный технический язык

- **SHOULD:** одно предложение передаёт одну основную мысль или инструкцию.
- **SHOULD:** называйте исполнителя и используйте активный залог, когда это возможно.
- **SHOULD:** в инструкциях обращайтесь к читателю прямо: «Запустите», «Проверьте», «Укажите».
- **SHOULD:** по возможности сообщайте условие перед действием, которое от него зависит.
- **MUST:** сохраняйте отрицания, исключения и ограничения; не сокращайте их ради стиля.
- **MUST:** используйте один термин для одной сущности. Сверяйтесь с [глоссарием](GLOSSARY.md).
- **SHOULD:** раскрывайте редкое сокращение при первом употреблении, если его значение не очевидно целевой аудитории.
- **MUST:** различайте наблюдение, вывод и рекомендацию. Помечайте вывод как вывод.
- **MUST:** настоящее время описывает текущее поведение; прошедшее — завершённую проверку или историческое состояние.
- **SHOULD:** посвящайте абзац одной теме и ставьте ограничение рядом с утверждением, к которому оно относится.
- **MUST:** в описаниях безопасности и публичных контрактов точность важнее краткости.

Не используйте слова «полностью», «безопасно», «бесшовно», «быстро» или «гарантирует» без условий и проверяемых данных. Не называйте функцию поддерживаемой только потому, что её имя есть в конфигурации или тесте.

Ориентир для английского текста: до 20 слов в инструкции и до 25 слов в описании. Это редакционный ориентир, а не требование CI. Для русского текста стремитесь к сопоставимой краткости без механического подсчёта. Обычно абзац содержит не более шести предложений.

### Примеры редакторской правки

Примеры основаны на контрактах и терминологии проекта. Формулировки «до» показывают типичную неясность, а не цитаты из конкретной версии документа.

**Процедура — проверка результата**

- До: «Запустите клиент; он работает.»
- После: «Создайте `server.txt` с действительной VLESS-ссылкой и ограничьте доступ к файлу. Запустите `reality-client --server-file server.txt --listen 127.0.0.1:1080`. Выполните `curl --socks5-hostname 127.0.0.1:1080 https://example.com`; успешный ответ подтверждает обработку этого запроса через локальный SOCKS5-вход, но сам по себе не подтверждает выбранный маршрут или работу TUN.»
- Причина: результат проверки отделён от вывода о сетевом соединении.

**Параметр API**

- До: «`base_dir` — папка конфигурации.»
- После: «В `rc_validate(config, base_dir)` параметр `base_dir` может быть `NULL`. См. [контракт библиотеки](LIBRARY.md).»
- Причина: указаны функция и допустимость `NULL`; утверждение сверено с контрактом `rc_validate`.

**Безопасность**

- До: «REALITY безопасно скрывает сервер.»
- После: «Если проверка REALITY не прошла, клиент не отправляет UUID VLESS этому серверу. Наблюдатель всё ещё может видеть IP-адрес сервера, время и объём соединения. См. [модель безопасности](SECURITY-MODEL.md).»
- Причина: абсолютное обещание заменено условием и явно указанной границей.

## Процедуры и предупреждения

Для процедуры выберите подходящие разделы:

1. Назначение и ожидаемый результат.
2. Предварительные условия: платформа, версия, зависимости, права, сеть и исходное состояние.
3. Предупреждение перед действием, способным нарушить сеть, изменить маршруты или раскрыть секрет.
4. Нумерованные шаги с одной основной целью в каждом.
5. Проверка результата, включая то, что проверка подтверждает и чего не подтверждает.
6. Диагностика: симптом → причина, которую нужно проверить → действие.
7. Ссылки на смежные справочники.

Не создавайте пустые разделы в короткой инструкции. **MUST:** разделяйте шаги для разных платформ; объясняйте заменяемые значения вроде `<SERVER>` и `<PATH>`; называйте требования `sudo`/администратора, перезагрузки и сетевого доступа; описывайте откат, если ошибка может лишить пользователя сети. Тексты ошибок и ожидаемый вывод сверяйте с кодом или тестом.

### Предупреждения

- **WARNING / ПРЕДУПРЕЖДЕНИЕ** — риск потери сети, утечки, раскрытия секрета или необратимого изменения системы.
- **IMPORTANT / ВАЖНО** — условие, без которого действие даст другой результат.
- **NOTE / ПРИМЕЧАНИЕ** — полезная деталь, не блокирующая выполнение.

Ставьте предупреждение непосредственно перед шагом, к которому оно относится. Пишите конкретно: риск, условие и способ снизить риск. Не используйте предупреждения как украшение.

### Короткие примеры оформления

Примеры показывают форму текста; проверяйте каждую реальную команду, схему и поведение по первоисточнику.

**CLI — проверенная команда из `docs/CLI.md`:**

```sh
reality-client --server-file server.txt --listen 127.0.0.1:1080
```

Перед командой укажите, что `server.txt` должен содержать, откуда взять файл и как ограничить к нему доступ. После неё назовите ожидаемый результат и отдельную проверку соединения.

**JSONC — это пример комментария, а не конфигурация проекта:**

```jsonc
{
  "field": "value" // Поясните поле; перед публикацией проверьте схему.
}
```

Не называйте этот блок строгим JSON и не копируйте фиктивное поле в рабочую конфигурацию.

**API — документируйте каждое поле по фактическому контракту:**

| Поле | Тип | Обязательно | Значение по умолчанию | Ошибка |
|---|---|---|---|---|
| `<точный путь поля>` | `<тип из реализации>` | `<да/нет>` | `<только подтверждённое>` | `<фактический ответ>` |

Плейсхолдеры в этой таблице не являются полями API. Замените их значениями из реализации, тестов и публичного контракта.

**TUN — сначала риск и платформа:**

> **ПРЕДУПРЕЖДЕНИЕ:** Следующий шаг изменит `<подтверждённое состояние сети>` на `<указанной платформе>`. Перед ним сохраните `<нужное исходное состояние>`; способ отката: `<проверенная процедура>`.

Заполните каждый плейсхолдер проверенной информацией. Не используйте предупреждение как готовую инструкцию, если риск или откат не подтверждены.

## Технические справочники и примеры

Для каждого параметра, флага или API-поля документируйте применимые пункты:

| Поле | Что зафиксировать |
|---|---|
| Имя и путь | Точное имя, регистр и путь поля |
| Тип | Строка, число, enum, массив, объект или nullable |
| Назначение | Какое поведение меняет параметр |
| Обязательность и значение по умолчанию | Только подтверждённые значения и область действия |
| Допустимые значения | Формат, диапазон и проверяемые ограничения |
| Совместимость | Поддерживаемая часть формата или собственное расширение |
| Ошибка | Фактическое поведение при неверном вводе |
| Пример и источник | Минимальный безопасный пример и ссылка на код, тест или заголовок |

Примеры должны соответствовать парсеру и реальной команде. Указывайте язык каждого блока: `json`, `jsonc`, `sh`, `powershell`, `rust` или `c`. Если JSON содержит комментарии, называйте его JSONC. Не помещайте реальные UUID, ключи, токены и пользовательские адреса. Не выдавайте поддержку части формата Xray или sing-box за полную совместимость.

### API, SDK и C ABI

**MUST:** сверяйте описание с публичным заголовком, реализацией FFI, тестами consumer и release workflow. Указывайте сигнатуры, допустимость `NULL`, возвращаемые значения, владение памятью, освобождение ресурсов, время жизни объектов, порядок вызовов, потоки, callback-и, re-entry и границы panic, когда они влияют на интеграцию. Различайте статическую и динамическую линковку и отдельно описывайте каждую платформу. Сборка или cross-link библиотеки не доказывает её работу на физическом устройстве.

## Архитектура

Для крупного компонента описывайте в подходящем порядке: цель → ответственность → входы → выходы → зависимости → обработка → инварианты → отказ → ограничения → источники и тесты. Разделяйте текущее состояние, механизм, причину решения и будущий план. Называйте существующие модули, функции, типы и пути. Добавляйте диаграмму только если она точна и помогает понять поток.

## Безопасность и доказательства

Формулируйте проверяемые утверждения по схеме:

> При **условии X** компонент обеспечивает **свойство Y**, кроме **случаев Z**. Свойство проверено **методом V** / **не проверено методом V**.

Не превращайте interop-тест в криптографическую гарантию. Не утверждайте анонимность, отсутствие всех DNS-утечек или безопасность любой конфигурации без модели угроз, условий и доказательств. Различайте внутреннее ревью, тест совместимости и независимый аудит. Для каждого результата проверки указывайте область охвата и дату или ссылку на актуальный workflow, если данные изменчивы.

## Статусы возможностей и платформ

Сохраняйте существующие статусы матрицы `docs/FEATURES.md`: «готово», «экспериментально», «не поддерживается», «проверено частично» и «не проверено на этой платформе». Английские эквиваленты: **ready**, **experimental**, **not supported**, **partially verified** и **not tested on this platform**. Не вводите синонимы без причины. Для каждой функции отдельно укажите реализацию, платформу и вид подтверждения. Не смешивайте:

- inbound и outbound, протокол и транспорт;
- библиотеку/ядро, CLI-клиент и готовое графическое приложение;
- компиляцию, cross-link, тест на runner-е, interop и выполнение на устройстве;
- экспериментальную функцию и опубликованную стабильную возможность;
- состояние `main` и содержимое опубликованного релиза.

Числа тестов, бенчмарков, платформ и версий указывайте с источником, датой и методикой. Не переносите результат одного сценария на все конфигурации.

- **SHOULD:** сохраняйте сопоставимую структуру, но переводите смысл, а не порядок слов.

## Markdown, ссылки и навигация

- **MUST:** у нового документа один логический H1. Двуязычные корневые документы могут иметь обоснованное исключение.
- **SHOULD:** используйте последовательную иерархию H2/H3; не добавляйте H4 без необходимости.
- **MUST:** применяйте нумерованный список для действий, маркированный — для независимых пунктов.
- **MUST:** оформляйте имена функций, типов, путей, команд и параметров как код.
- **SHOULD:** выбирайте таблицу для компактного сравнения полей или вариантов, а связный текст — для объяснения алгоритма.
- **MUST:** проверяйте относительные ссылки и якоря после изменения заголовков.
- **MUST:** не оставляйте ссылки на отсутствующие файлы, разделы, кнопки или неподтверждённые артефакты.
- **MUST:** не удаляйте уникальные сведения, пока не указано их новое каноническое место.
- **SHOULD:** в длинных документах добавляйте оглавление и понятные заголовки.
- **MUST:** не меняйте upstream- и автоматически созданные файлы ради редакционного единообразия.

## Примеры редакторских решений

Примеры ниже показывают, как сделать утверждение проверяемым и не расширить его смысл. Формулировки «до» намеренно неполны; они не являются текущим описанием проекта.

### Инструкция с проверкой результата

**До:** «Проверьте файл настроек.»

**После:** «Запустите `reality-client --config config.json --check`. Если настройки корректны, CLI выведет `настройки в порядке` и завершится до вызова `app.start`. Эта проверка не подтверждает сетевое подключение.»

**Почему:** действие, ожидаемый результат и граница проверки следуют из [CLI](CLI.md) и [обработчика команды](../bin/client/src/main.rs).

### Описание параметра

**До:** «`cache_capacity` ограничивает число DNS-ответов.»

**После:** «`cache_capacity` задаёт максимальное число записей DNS-кеша. Ключ записи — имя запроса и тип DNS-записи; записи одного имени типа A и AAAA считаются отдельно.»

**Почему:** описание называет единицу параметра и не смешивает ответы с записями кеша; см. [DNS](DNS.md) и [реализацию кеша](../core/src/app/dns/cache.rs).

### Утверждение о безопасности

**До:** «`allow_insecure` отключает проверку TLS.»

**После:** «Для VLESS/Trojan с `security=none` соединение не шифруется. Ядро пропускает такой сервер, если `allow_insecure` не включён.»

**Почему:** точный текст указывает конкретный режим и его последствие, не приписывая параметру отключение проверки сертификата; см. [CONFIG](CONFIG.md) и [разбор конфигурации](../core/src/app/config/singbox.rs).

## Сопровождение стандарта

Перед изменением документа определите его класс и основной источник фактов. В pull request приложите ссылки на источники и укажите необходимые проверки. Для документальных изменений запустите `git diff --check` и `python scripts/check_doc_links.py`; проверьте языковую пару, команды и примеры. При изменении заголовка C ABI дополнительно запускайте `python scripts/check_ffi_abi.py`. CI должен проверять актуальный head PR, прежде чем его объединят.

Объём проверки соразмеряйте изменению: проверьте изменённый текст и связанные с ним утверждения. Исправление опечатки само по себе не требует полной технической ревизии документа. Старую документацию можно приводить к стандарту постепенно; однако обнаруженную существенную ошибку нельзя считать подтверждённой или оставлять без фиксации только потому, что исправление выходит за рамки текущей правки. Зафиксируйте её для отдельного изменения.

Ошибку реализации фиксируйте отдельно. Этот стандарт не разрешает менять код, публичный API/ABI, формат конфигурации или поведение протоколов ради документации. Сторонние файлы в `vendor/` исключены, если только не редактируется собственное пояснение проекта.
