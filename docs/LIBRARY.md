# Ядро как библиотека

SDK-архивы с библиотекой, заголовком C ABI и примером публикуются на странице
[Releases](https://github.com/ERGFT/vpn-core/releases) при версионированном
выпуске. Если архива для вашей платформы там ещё нет, соберите библиотеку из
исходников по инструкции ниже. Выберите архив по целевой платформе; не
переносите бинарник между разными ОС или архитектурами.
Внутри архива есть `include/reality.h`, библиотека в `lib/`, пример на C и
локальные копии этого руководства и документации API.

Опубликованный архив `v0.1.0` создан до добавления manifest, CMake и
pkg-config metadata и не содержит их. Ниже описана упаковка, которую создаёт
текущий release workflow на `main`; она появится в последующем выпуске и не
добавляется задним числом в `v0.1.0`.

Версионированный release workflow собирает SDK для Linux x86_64, Windows
x86_64, macOS arm64, Android arm64-v8a и iOS arm64. Для каждого ZIP рядом
публикуется файл `.sha256`. CI проверяет состав ZIP и checksum; пример C из
распакованного SDK собирается и запускается на Linux, Windows и macOS.
Android и iOS проверяются кросс-компоновкой примера. Эти проверки мобильных пакетов не
заменяют запуск на устройстве. Списки лицензий зависимостей, SBOM и build
provenance публикуются отдельными файлами релиза.

В SDK ZIP, собранных текущим workflow из `main`, есть `manifest.json` со схемой
`schema_version: 1`. В нём указаны версия/тег, платформа и Rust target triple,
версия `rustc`/Cargo и ОС сборочного
раннера. Для каждого файла, кроме самого manifest, записаны относительный путь,
размер и SHA-256; для библиотек также указан тип (`shared`, `static` или `import`).
Поле `static_link.arguments` содержит native linker arguments, которые `rustc`
вывел для static library конкретной target-сборки.
Перед подключением проверьте ZIP и manifest одной командой из клона репозитория
(пример для Linux; имя платформы должно совпадать с архивом):

```sh
python scripts/check_ffi_sdk.py linux-x86_64 vpn-core-sdk-linux-x86_64.zip
```

Проверка читает соседний `.sha256`, проверяет ZIP и сверяет состав, размеры и
SHA-256 файлов с `manifest.json`. Доступные платформы: `linux-x86_64`,
`windows-x86_64`, `macos-arm64`, `android-arm64-v8a`, `ios-arm64`.
`minimum_os` содержит минимальную версию, явно заданную сборкой
(сейчас iOS 13.0); `null` означает, что проект отдельно её не объявляет — это не
гарантия совместимости со всеми версиями ОС. Неизвестные поля потребителям следует
игнорировать. Несовместимые изменения структуры требуют увеличения `schema_version`.

## Подключение C/C++ проекта

Каждый архив, собранный текущим workflow, содержит relocatable CMake package в
`cmake/vpn-core/`. Путь до библиотек и заголовка вычисляется относительно
config-файла, поэтому SDK можно
перемещать и распаковывать в каталог с пробелами. Минимальный CMake 3.15:

```cmake
find_package(vpn-core CONFIG REQUIRED
    PATHS "${VPN_CORE_SDK}/cmake/vpn-core"
    NO_DEFAULT_PATH
    NO_CMAKE_FIND_ROOT_PATH)

add_executable(my_app main.c)
target_link_libraries(my_app PRIVATE vpn-core::vpn-core)
```

Передайте путь к распакованному архиву при конфигурации своего проекта:

```sh
cmake -S . -B build -DVPN_CORE_SDK="/path/to/vpn-core-sdk"
cmake --build build --config Release
```

Переменная `VPN_CORE_SDK` должна указывать на каталог с `include/`, `lib/` и
`cmake/`, а не на сам ZIP.

`vpn-core::shared` доступен там, где архив содержит динамическую библиотеку;
`vpn-core::static` — статическую. У Windows shared target использует DLL вместе
с import library. Универсальный target `vpn-core::vpn-core` выбирает shared,
если он есть, иначе static. В текущей упаковке Linux, Windows, macOS и Android
содержат shared и static варианты; iOS содержит только static библиотеку.
Поэтому `vpn-core::shared` на iOS отсутствует, а универсальная цель выбирает
там static. Статический target получает native зависимости из того же
`rustc --print=native-static-libs` вывода, который записан в manifest. iOS ZIP
содержит обычную `libreality.a`, не XCFramework.
Для Android и iOS передайте путь SDK проекту с подходящим NDK/iOS CMake
toolchain; `NO_CMAKE_FIND_ROOT_PATH` не даёт Android NDK перенаправить явный
поиск SDK в sysroot. Cross-link проверка не подтверждает запуск на устройстве.

В архивах Linux и macOS, собранных текущим workflow, рядом с библиотекой есть
`lib/pkgconfig/vpn-core.pc`:

```sh
export PKG_CONFIG_PATH="$VPN_CORE_SDK/lib/pkgconfig${PKG_CONFIG_PATH:+:$PKG_CONFIG_PATH}"
pkg-config --cflags --libs vpn-core
pkg-config --static --libs vpn-core  # включает зависимости статической библиотеки
```

Пути в `.pc` вычисляются от `${pcfiledir}`, поэтому metadata работает после
перемещения SDK. Для Windows и мобильных платформ используйте CMake.

Для совместных правил приложений/сайтов добавлен `rc_set_connection_owner`:
[контракт, fail-closed и интеграция Android](APPLICATION_ROUTING.md).

Ядро можно встроить прямо в приложение — Android (`VpnService`), iOS
(Network Extension), десктопный клиент — вместо того чтобы запускать
`reality-client` отдельным процессом. Интерфейс — C ABI: подходит для
Kotlin/Java (JNI), Swift, C/C++, Go (cgo), C# (P/Invoke), Python (ctypes) и
всего, что умеет вызывать функции C.

- Заголовок: [`ffi/include/reality.h`](../ffi/include/reality.h).
- Минимальный пример встраивания: [`ffi/examples/minimal.c`](../ffi/examples/minimal.c).
- Код: [`ffi/src/lib.rs`](../ffi/src/lib.rs), пример на C —
  [`ffi/examples/smoke.c`](../ffi/examples/smoke.c) (его собирает и
  запускает `scripts/ffi_smoke.sh`).
- Готовые JNI/Kotlin- и Swift-обёртки не поставляются; приложение вызывает C ABI
  и реализует платформенный bridge самостоятельно.
- Ядро распространяется по GPL-3.0-or-later. FSF рассматривает статическую
  и динамическую компоновку GPL-программы с другими модулями как создание
  совокупного произведения, на которое распространяются условия GPL. Для

## Совместимость C ABI

Публичные C-сигнатуры функций, `typedef`-ы и числовые значения `RC_*` enum зафиксированы в
[`ffi/abi-baseline.json`](../ffi/abi-baseline.json). Linux CI сверяет этот
снимок с C-заголовком и экспортами Rust, поэтому случайное удаление/переименование
функции, изменение типа аргумента/результата, изменение callback typedef-а или
перенумерация кода ошибки остановят PR. Новую функцию можно добавить только
явно обновив снимок и проверив совместимость потребителей. Изменение уже
опубликованного API считается breaking change: его нужно отдельно спланировать
и описать до выпуска.

Локальная проверка: `python scripts/check_ffi_abi.py`; тесты самого проверяющего
скрипта: `python scripts/test_check_ffi_abi.py`. Флаг `--update-baseline` меняет
снимок автоматически, поэтому используйте его только после проверки diff и
обсуждения совместимости в PR.

## Сборка

```sh
cargo build --release -p reality-ffi
# Linux/Android: libreality.so и libreality.a; macOS: libreality.dylib и .a;
# Windows: reality.dll + reality.dll.lib и reality.lib; iOS: только libreality.a.
```

Под Android — через [cargo-ndk](https://github.com/bbqsrc/cargo-ndk):

```sh
cargo ndk -t arm64-v8a -t armeabi-v7a -t x86_64 -o app/src/main/jniLibs \
    build --release -p reality-ffi
```

Под iOS — `IPHONEOS_DEPLOYMENT_TARGET=13.0 cargo build --release -p
reality-ffi --target aarch64-apple-ios` (статическая `libreality.a`; workflow
не упаковывает её в XCFramework). Минимальная версия iOS нужна одна для Rust и
для C-кода
aws-lc: без неё aws-lc собирается под iOS из SDK, а Rust линкует под
10.0 — ошибка `___chkstk_darwin`.

## Жизненный цикл

```c
#include "reality.h"

char *err = NULL;
RcCore *core = rc_start(config_json, base_dir, /*tun_fd*/ -1, &err);
if (!core) { printf("ошибка: %s\n", err); rc_free_string(err); return; }

int status;
char *proxies = rc_request(core, "GET", "/proxies", NULL, &status);
/* … */
rc_free_string(proxies);

rc_stop(core);
```

- **`rc_start(config, base_dir, tun_fd, &err)`** — настройки текстом (JSON
  sing-box или Xray-core, как для `reality-client --config`), папка для
  относительных путей в них (базы geosite/geoip, наборы правил, кеши
  подписок), дескриптор TUN на Unix или -1. На Windows готовый дескриптор
  передать нельзя; другие отрицательные значения тоже отклоняются. На Unix,
  если передан дескриптор (значение >= 0), владение сразу переходит ядру,
  в том числе при ошибке запуска. При ошибке возвращается NULL и текст в
  `err`.
- **`rc_request(core, method, path, body, &status)`** — синхронные запросы к
  локальному API ([API.md](API.md)), тем же путём и с тем же ответом, без
  сети и токена. Потоки `/events`, `/traffic`, `/memory`, `/logs` и
  WebSocket-поток `/connections` через эту функцию недоступны: события и
  журнал передаются callback-ами; потоковые данные трафика и памяти в режиме
  библиотеки не предоставляются. Обычный `GET /connections` возвращает один
  снимок. Доступны запросы к группам и выбору сервера (`/proxies`), режиму
  (`PATCH /configs`), проверка задержки, подписки (`/providers/proxies`),
  DNS и статистике (`/stats`).
  Ответ — JSON (пустая строка у 204), код — в `status`.
- **`rc_reload(core, config, &err)`** — новые настройки без разрыва
  соединений; ошибка — работают прежние. Ответ — `{"notes": […]}`: что
  вступит в силу только после перезапуска.
- **`rc_network_changed(core)`** — сообщить о смене сети, которую обнаружило
  приложение-хост. Ядро очищает DNS-кеш и кеш IP-адресов серверов, отменяет
  отслеживаемые TCP/UDP-соединения и оставляет входы и текущие настройки
  работать. Новые соединения заново разрешают имена; автоматического
  переподключения пользовательских потоков нет — приложение должно повторить
  запросы по своей политике. Возвращает `0` при обработке, `-1` для NULL
  handle или внутренней ошибки.
- **`rc_set_protect(cb, user)` и `rc_set_connection_owner(cb, user)`** —
  process-wide callbacks для защиты сокетов и определения UID. Они должны быть
  потокобезопасными и быстро возвращаться. Замена или снятие ждёт активный
  вызов; поэтому callback не должен вызывать собственную setter-функцию — она
  будет ждать завершения самого себя. После возврата setter-функции прежние
  callback и `user` можно освободить.
- **`rc_set_event_callback(core, cb, user)`** — события (как поток
  `GET /events`): открытие и закрытие соединений, переключение групп,
  обновление подписок, перечитывание, смена режима. Callback получает
  временную JSON-строку из фонового потока. `cb = NULL` снимает подписку;
  замена или снятие ждут текущий callback. После возврата можно освободить
  старые `cb` и `user`.
- **`rc_set_log_callback(core, level, cb, user)`** — журнал ядра. На
  уровне `info` (по умолчанию) адресов сайтов в нём нет; на уровне
  `debug` (и `RUST_LOG=debug`) в журнал — и в обратный вызов, и в
  `GET /logs` — попадают домены посещаемых сайтов и результаты DNS. Не
  отправляйте такой журнал на сервер и не показывайте его без ведома
  пользователя. Снятие и замена callback имеют тот же барьер завершения.
- **Контракт callback:** callback-функции могут вызываться одновременно из
  потоков ядра; синхронизируйте общее состояние и не блокируйте поток ядра
  надолго. Любой callback должен вернуться обычным образом: не выпускайте
  C++-исключения, Rust panic или `longjmp` через C ABI; ловите C++-исключения
  внутри callback. Event/log callback не должны вызывать функции для того же
  `RcCore`; их JSON и адресные строки действуют только до возврата callback,
  а контекст `user` должен жить до снятия callback или возврата `rc_stop`.
- **`rc_stop(core)`** — остановить: входы закрываются, маршруты `auto_route`,
  которыми управляет ядро, снимаются. При внешнем TUN маршрутами и kill switch
  управляет встраивающее приложение. Перед возвратом функция дожидается
  завершения обратных вызовов; после возврата новые вызовы callback не начнутся. Данные `user`
  и связанные с callback ресурсы можно освобождать после `rc_stop`. `NULL`
  допустим и ничего не делает.
- **`rc_free_string(s)`** — освободить строку, которую вернула библиотека.

После `rc_is_alive(core) == 0` причину можно получить через
`rc_last_error_code(core)` и `rc_last_error_message(core)`. Код опрашивает
терминальную ошибку без ожидания и остаётся той же при повторном чтении до
`rc_stop`; после остановки handle недействителен, читать из него нельзя.
Ошибки отдельных `rc_request` и `rc_reload` возвращаются самими вызовами и не
меняют терминальное состояние здорового ядра. Значения
`RC_ERROR_*` стабильны для ABI: `0` — ошибки пока нет, `-1` — NULL handle,
`1` — конфигурация/запуск, `2` — ввод-вывод, `3` — соединение заблокировано
маршрутом, `4` — протокол/соединение, `5` — TLS, `6` — DNS-имя,
`7` — ошибка аутентификации, `255` — внутренняя ошибка границы C ABI.
`rc_last_error_message` возвращает короткий текст на английском или пустую
строку, если ошибки нет. Для NULL это `Invalid core handle`. Подробный текст
исходной ошибки не раскрывается: он может содержать адреса и значения
настроек. Полученную строку освобождайте через `rc_free_string`.

### Краткая таблица C ABI: NULL, результаты и владение

| Функция | NULL и результат | Память и время жизни |
| --- | --- | --- |
| `rc_version` | Аргументов нет; возвращает версию | Указатель на статическую строку; освобождать не нужно |
| `rc_validate` | `config` обязателен, `base_dir` может быть NULL; `1` — настройки приняты, `0` — ошибка | Выделяемой строки нет; подробная ошибка не возвращается |
| `rc_start` | `config` обязателен; `base_dir` и `error` могут быть NULL; `NULL` handle означает ошибку | Только при ошибке `error` получает строку — освободите её через `rc_free_string`; handle освобождается через `rc_stop`; Unix FD переходит ядру при вызове, в том числе если запуск завершился ошибкой |
| `rc_request` | `method` и `path` обязательны; `body` и `status` могут быть NULL; ошибки аргументов возвращаются как JSON | Возвращаемую строку всегда освобождает host через `rc_free_string`; `status` записывается, только если он не NULL |
| `rc_reload` | `config` обязателен, `error` может быть NULL; `NULL` результат означает ошибку | Успешный JSON или строку `error` освобождает host через `rc_free_string`; `error` заполняется только при ошибке |
| `rc_is_alive` / `rc_last_error_code` | NULL handle даёт `0` / `RC_ERROR_INVALID_HANDLE` | Только скалярный результат; использовать лишь живой handle |
| `rc_last_error_message` | Для NULL handle возвращается `Invalid core handle`; при отсутствии ошибки — пустая строка | Возвращаемую строку всегда освобождает host через `rc_free_string` |
| `rc_network_changed` | NULL handle даёт `-1`; `0` означает, что сигнал обработан | Только скалярный результат; использовать лишь живой handle |
| `rc_stop` | NULL — безопасная пустая операция | Освобождает handle; вызывать один раз, затем указатель больше не использовать |
| `rc_set_event_callback` / `rc_set_log_callback` | NULL callback снимает подписку; NULL handle или неверный уровень журнала даёт `-1` | После возврата из замены/снятия прежние callback и `user` можно освободить; для журнала NULL `level` означает `info` |
| `rc_set_protect` / `rc_set_connection_owner` | Настройка на весь процесс; NULL callback снимает её; функции не возвращают статус | Старый `user` можно освободить после возврата из снятия/замены |
| `rc_set_lock_dir` | NULL или не UTF-8 строка даёт `-1`; принятие UTF-8 строки — `0`; каталог и его права не проверяются | На Windows принимается только первый путь; на других системах настройка не действует; строка нужна только во время вызова |
| `rc_free_string` | NULL — безопасная пустая операция | Принимает только ещё не освобождённую строку, возвращённую этой библиотекой |

NULL допустим только там, где это явно указано. Любой ненулевой указатель
должен указывать на доступную память нужного размера; входные C-строки должны
быть корректно завершены нулём. C ABI не может безопасно проверить произвольный
или уже освобождённый указатель. Handle нельзя использовать после `rc_stop`;
все операции с одним живым handle приложение сериализует.

### Граница panic

Только функции, которые явно преобразуют panic в свой код/результат ошибки,
могут вернуть такой fallback, и лишь при сборке с `panic = "unwind"`. Это не
изоляция процесса и не обещание восстановления после произвольной panic во
всех экспортированных функциях. При `panic = "abort"` процесс-хост завершается;
некорректные указатели также не становятся безопасными благодаря `catch_unwind`.
Panic, C++-исключения и `longjmp` из callback не должны пересекать C ABI.

Вызывайте `rc_network_changed` только после сигнала от host API платформы
(например, смены Wi-Fi/cellular или default route). Ядро не опрашивает ОС и не
определяет доступность Интернета. Повторный сигнал также отменит соединения,
открытые после предыдущего; объединяйте дублирующие уведомления на стороне
приложения. Эта функция не пересоздаёт TUN descriptor, VPN permission, route
или параметры системного интерфейса: при пересоздании этих ресурсов ядро
нужно остановить и запустить заново.

Функции можно вызывать из любого потока, но операции с одним `RcCore`
сериализует приложение; нельзя вызывать `rc_is_alive`, функции диагностики
или другие операции одновременно на том же handle, а после `rc_stop` handle
недействителен. Event/log callbacks идут из фоновых потоков ядра. Они должны
быстро переложить данные в свой поток и вернуться. Не вызывайте функции для
того же `RcCore` из callback: операции блокируют друг друга, а `rc_stop` и
снятие подписки ждут его возврата.

## SOCKS5 как выход

Ядро может отправлять TCP-соединения через SOCKS5 proxy из sing-box-конфига.
Укажите `network: "tcp"`, чтобы не включать неподдерживаемую UDP-сеть.
Минимальный пример для `rc_start`:

```json
{
  "outbounds": [
    { "type": "socks", "tag": "upstream", "server": "proxy.example", "server_port": 1080, "network": "tcp" }
  ],
  "route": { "final": "upstream" }
}
```

Для аутентификации задайте `username` и `password`; расширение vpn-core
`password_file` позволяет хранить пароль отдельно. Ограничьте доступ к этому
файлу средствами ОС. Учётные данные не выводятся при форматировании
конфигурации через `Debug`. Поддерживается только TCP CONNECT: UDP ASSOCIATE
и TLS до самого proxy пока не поддерживаются. При отказе proxy это соединение
завершается ошибкой.
SOCKS5 не шифрует соединение с самим proxy; RFC 1929 передаёт пароль без
шифрования. Используйте такой proxy только в доверенной сети или поверх
отдельного защищённого транспорта.

## HTTP CONNECT как выход

Для исходящих TCP-соединений через HTTP/1.1 proxy используйте `type: "http"`:

```json
{
  "outbounds": [
    {
      "type": "http",
      "tag": "upstream",
      "server": "proxy.example",
      "server_port": 8080,
      "username": "user",
      "password_file": "proxy.pass",
      "tls": { "enabled": true, "server_name": "proxy.example" }
    }
  ],
  "route": { "final": "upstream" }
}
```

Аутентификация использует Basic и передаётся только после установления TLS,
если `tls.enabled` включён. Проверка сертификата обязательна и использует
встроенные публичные корни; `tls.server_name` задаёт SNI и имя проверки, по
умолчанию используется `server`. Расширение vpn-core `ca_file` указывает PEM-файл
дополнительных корневых сертификатов. Для обычного HTTP proxy поле `tls` можно
опустить. Поддерживается только CONNECT через HTTP/1.1: произвольные заголовки,
HTTP/2, HTTP/3 и UDP не поддерживаются. Ошибка proxy возвращается вызывающему
коду; автоматического перехода на `direct` нет. Пароль можно задать строкой
`password` либо расширением vpn-core `password_file`, но не обоими сразу.

## TCP-цепочки через `detour`

Для SOCKS5- и HTTP CONNECT-outbound можно задать `detour`: тогда ядро откроет
соединение к серверу proxy через указанный TCP outbound. Например, HTTP CONNECT
можно направить через SOCKS5:

```json
{
  "outbounds": [
    { "type": "socks", "tag": "entry", "server": "entry.example", "server_port": 1080, "network": "tcp" },
    { "type": "http", "tag": "exit", "server": "exit.example", "server_port": 8080, "detour": "entry" }
  ],
  "route": { "final": "exit" }
}
```

`detour` задаётся у SOCKS5 или HTTP CONNECT. Цепочку можно продолжить ещё одним
таким выходом; базовым outbound может быть `direct`, VLESS или Trojan.
Группы, `block` и `dns` нельзя использовать как `detour`. Конфигурация с
отсутствующим tag или циклом отклоняется. Отказ любого звена возвращается
вызывающему коду; автоматического перехода на `direct` нет. Поддерживается TCP,
UDP-цепочки не поддерживаются.

## Android

До передачи FD можно вызвать `rc_validate(config, base_dir)` — 1 означает,
что разбор и построение настроек прошли, 0 — ошибку без потенциально секретного
текста. Проверка читает файлы (CA, правила), но не запускает входы и не проверяет
разрешение VPN, FD или доступность сети. Успех не гарантирует успех `rc_start`.

На живом handle `rc_is_alive(core)` возвращает 1, пока в канале задач нет
терминальной ошибки, и 0 после ошибки (повторные вызовы остаются 0). NULL — 0.
Это не ping, не проверка интернета и не полный контроль всех фоновых задач.
Ошибки задач, созданных через `spawn_task`, включая unwind-панику, доходят
до этого канала. `panic=abort` перехватить нельзя. `Running::wait` сохраняет
ошибку после предварительного опроса. После ошибки приложение останавливает
ядро и сообщает пользователю; автоматическое переключение на прямую сеть
не выполняется библиотекой.

После `rc_is_alive(core) == 0` используйте `rc_last_error_code` и
`rc_last_error_message`, чтобы выбрать безопасное сообщение приложению или
политику восстановления. Текст намеренно общий и не содержит адреса сервера,
UUID, ссылку или секреты конфигурации. Повторный опрос возвращает ту же
терминальную ошибку; вызовы с одним handle сериализуются приложением.

Для внешнего TUN имена VPN/DoH-сервера не должны разрешаться через DNS,
который сам требует соединения с этим VPN-сервером. Укажите расширение
vpn-core `dns.bootstrap` с tag прямого UDP DNS-сервера, заданного IP-адресом
([DNS.md](DNS.md)). Без него разрешение имени транспорта завершается ошибкой,
а не системным/прокси fallback. Этот прямой DNS видит имена транспортных
серверов; обычные запросы приложений продолжают использовать свои правила.
Системный `local` DNS с внешним TUN отклоняется из-за петли.

1. `VpnService.Builder` — адреса, маршруты (`addRoute("0.0.0.0", 0)`),
   DNS, `establish()` → `ParcelFileDescriptor`.
2. До `rc_start` — `rc_set_protect`: обратный вызов, который вызывает
   `VpnService.protect(fd)` для каждого сокета ядра (соединения к
   серверу, `direct`, DNS) — иначе они ушли бы в свой же VPN.
3. `rc_start(config, filesDir, pfd.detachFd(), &err)` — владение
   дескриптором переходит ядру при вызове: ядро закроет его и при ошибке
   запуска, и в `rc_stop` после успешного запуска. В настройках —
   вход `{"type": "tun", "tag": "tun"}`: адреса, маршруты и kill switch
   задаёт `VpnService`, поэтому `auto_route`/`strict_route` не
   применяются. Перехват DNS (`hijack-dns`), sniffing, fake-IP работают
   как обычно.

Набросок JNI-обёртки (Kotlin):

```kotlin
object Core {
    init { System.loadLibrary("reality") }       // libreality.so
    external fun start(config: String, dir: String, tunFd: Int): Long   // 0 — ошибка
    external fun request(core: Long, method: String, path: String, body: String?): String
    external fun stop(core: Long)
}
```

C-часть обёртки (`jni.c`) вызывает `rc_start`/`rc_request`/`rc_stop`, а
`rc_set_protect` — с обратным вызовом, который через `JNIEnv` (поток —
`AttachCurrentThread`) вызывает `VpnService.protect(int)`.

## iOS, macOS

В `NEPacketTunnelProvider` дескриптор utun можно найти среди открытых
дескрипторов процесса (так делают WireGuard и sing-box) и передать в
`rc_start`. Сокеты ядра в Network Extension идут мимо туннеля и без
`rc_set_protect`.

## Десктоп

Проще всего — `rc_start(config, dir, -1, …)` с настройками, как для
`reality-client`: вход `tun` сам создаёт интерфейс и маршруты (нужны
права администратора или root), `mixed` — прокси. Управление —
`rc_request`, без HTTP.

На Windows один раз до `rc_start` вызовите `rc_set_lock_dir(dir)` с каталогом
для файла блокировки `auto_route`. Приложение должно защитить каталог так,
чтобы писать могли только SYSTEM и администраторы (как
`%ProgramData%\RealityClient` у `reality-client`). Функция проверяет только,
что строка не NULL и содержит корректный UTF-8; она не проверяет существование
каталога или его права. Если файл блокировки не удаётся открыть или он уже
занят другим экземпляром, запуск TUN с `auto_route` завершится ошибкой.
Повторный вызов не заменит первый путь. На других системах настройка не
действует.

## Проверка

- `cargo test -p reality-ffi` — вызовы C ABI из Rust (на Linux и
  Windows в CI);
- `scripts/ffi_smoke.sh` — настоящая программа на C: запуск, ошибка
  настроек, `rc_request` (выбор сервера, режим, 404), трафик через
  SOCKS5-вход ядра к эхо-серверу, события в обратный вызов,
  `rc_set_protect` для сокетов ядра, `rc_reload`, `rc_stop`; с root — ещё
  запуск с готовым дескриптором TUN (как от `VpnService`).
- Smoke проверяет, что ошибочные аргументы `rc_request` и ошибка `rc_reload`
  не превращаются в терминальную ошибку, а снятие event callback дожидается
  завершения текущего вызова и дальше не использует `user`. Rust unit test
  проверяет закрытие gate при уже выполняющемся callback.
- Пример из распакованного SDK запускается на Linux, Windows и macOS. Он
  проверяет ошибку конфигурации с освобождением строки, три цикла
  `rc_start`/`rc_request`/`rc_stop` и безопасный `rc_stop(NULL)`. Linux smoke
  дополнительно проверяет, что после возврата `rc_stop` callback больше не
  вызывается.
